**A real statement now reads end to end.** Ten owner-driven reads on 2026-07-25 took the parser from "no PDF opens at all" to 233 rows across 12 pages reaching the account-binding stage, correcting eleven real defects on the way (D-023 … D-032). **Month-to-month stability is now evidenced, 2026-07-28.** The readers had only ever met two or three real documents per layout, so nothing said whether a layout held across months or had been fitted to the first documents read. A throwaway harness ran the real `readStatement` over all 16 files in `shared-statements/`: **15 of 15 genuine statements read and cross-checked**, 1,465 rows over 73 pages — SCB 12/12 across twelve consecutive months (**1,143 rows**, 4–6 pages each), Krungthai 1/1 (233 rows), KBANK 2/2 (55 and 34 rows). **Two figures corrected 2026-07-29** by an independent re-run during task 18: the SCB subtotal read 1,053, which cannot be right because 1,053 + 233 + 55 + 34 is 1,375 rather than the 1,465 total stated in the same sentence; and the page count read 75 against 73 for the fifteen genuine statements (76 including the three-page reference sheet). That is the fail-closed path working, not a defect. The harness was deleted after the run — it reads real statements and so cannot be a committed test; recreate it when a new layout or a new month needs checking.

**All three statement layouts now read.** Masked dumps of 12 SCB and 2 KBANK statements on 2026-07-26 produced `docs/SCB_CONTRACT.md` and `docs/KBANK_CONTRACT.md`, and `lib/statement-layout.ts` reads both. Direction now comes from the balance chain and is cross-checked against that geometry, failing closed on disagreement. `lib/krungthai-layout.ts` is untouched apart from carrying its contract version, as the design decision required.

Migration `202607260009_multi_bank_layouts.sql` admits the two new banks through `confirm_import` (D-041). Widening the CHECK constraints was not the half that mattered: the RPC recomputed every row fingerprint with a hard-coded `'KTB'`, so an SCB import would have failed with `fingerprint mismatch` no matter how correct the client was. The bank code now comes from the bound account, and a contract version may only be confirmed into an account at the bank that layout reads.

**A backup now restores into a project that never held it** (D-044). A second local Supabase project, `private-ledger-recovery`, runs alongside the primary one bound to a different invented owner; `tests/recovery-portability.test.ts` exports from the primary over HTTP under a real aal2 session, encrypts and decrypts the artifact, and stages, chunks and commits it into the destination under that project's own aal2 session. A second project rather than a second database because the ledger schema depends on `auth` in 24 places and a bare `createdb` has no such schema at all. It found what a same-project round trip structurally cannot: an owner id embedded inside `overlay_revisions.snapshot`, which every column-level check looks past. The restore-request builder moved out of test code into `lib/restore-plan.ts`, because recovery is the one path that must work on a machine that has lost everything else.

**The app can create a ledger account** (D-045, migration 010). Until 2026-07-27 every account came from the seed, because `public.accounts` grants `authenticated` select only — so a statement printing a suffix no seeded account carried could be read, cross-checked and then bound to nothing, which is exactly what both real statements did. `public.mutate_account` is now the single write path, modelled on `mutate_category`, and the bind stage offers a form precisely when no loaded account matches the statement's bank and last four. Create and relabel only: `bank_code` is hashed into every row fingerprint and `last_four` is what binding matches, so both are identity and a relabel carrying either is refused rather than ignored.
