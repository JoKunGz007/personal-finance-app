## D-060 — Three real slip references reached the test fixtures, and the entries claiming otherwise are wrong

- Date: 2026-07-31
- Status: Accepted by the owner as an exposure he is content with; **not remediated**. Corrects three earlier entries rather than superseding their decisions — every design decision in D-056, D-057 and D-059 stands. What is wrong in them is a factual claim, not a judgement.
- **The false claims, named so they are not re-read as true.** D-056's evidence line says "Every fixture is built by `buildSlipQrPayload` from an invented reference — the builder lives in `lib/` precisely so no test input is ever copied off a real slip". D-057 repeats "from an invented reference". `tests/e2e/owner-session.spec.ts` said "No real slip reference exists in this repo." All three are false. `DECISIONS.md` is append-only, so they stay as written and this entry is the correction; the source comments, which are not append-only, have been fixed in place.
- **What is actually in the repository:** three real transaction references, copied from `receipts_sample/` — one in `tests/fixtures/synthetic-slip.ts` (`KTB_SLIP_DATED`) and the same one plus two others in `tests/slips.test.ts` (a Krungthai 17-character reference and a KBANK one). They are committed and pushed. The other fixtures are genuinely invented.
- **How it happened, which is the part worth keeping.** The structural probe in D-056 was written to be value-free, but its reportable-tag whitelist assumed a flat TLV and the payload nests everything inside tag `00` — so it printed whole references (already recorded in GOTCHAS). At the time this was noted as a read rather than a write, with the explicit remark that nothing derived from it would reach a fixture. Hours later, writing tests that needed reference *shapes* per bank, three of those shapes were reproduced from what had been printed. The gap was not carelessness about the rule; it was that **the rule was applied at the moment of the leak and not at the moment of reuse**, by which point the values looked like ordinary knowledge of the format.
- Consequence for `docs/FIXTURE_POLICY.md`: its central rule — "No real value becomes a fixture, ever" — is intact as a rule and is now **violated in practice**. The policy is not amended; a breach that is recorded is better than a policy quietly narrowed to fit what happened.
- Decision (the owner's): the exposure is accepted and the references stay. Recorded because the alternative — swapping three strings — is a few minutes' work, so leaving them is a choice rather than an obstacle. **Still open, and cheap, whenever it is wanted:** replace the three with invented values of the same shape. Note that a forward commit does not remove them from history or from the remote; only a history rewrite and force-push would, which is a separate decision nobody has asked for.
- **The generalisable lesson, which is not "be careful":** a value-free reporting rule protects the moment a value is *printed*. It does nothing at the moment that value is *reused*, because by then it is indistinguishable from format knowledge the agent legitimately has. Where a fixture must reproduce a real *shape*, generate the shape from the grammar — `buildSlipQrPayload` already existed for exactly this and was used for the payloads while the references it was given were pasted.
- Evidence: `tests/fixtures/synthetic-slip.ts`, `tests/slips.test.ts`, both now carrying comments that say which references are real. Found when the owner captured a Krungthai slip through the UI and its printed reference was visibly identical to the "invented" fixture — that is, by using the product, not by any check in the suite. No automated check exists that would have caught it, and none is added here.

## D-061 — The app becomes four routes, and the shell owns everything that is not one surface's business

- Date: 2026-07-31
- Status: Accepted and built. The routing half of `PLAN.md` task 19; it creates nothing hosted and needed no authorization. The OAuth half of that task is untouched.
- Context: the app was one long page. That had already been worked around once — on 2026-07-29 the ledger view was moved above the import bench because reaching it meant scrolling past everything else (task 17), which is a plaster over the fact that four unrelated surfaces shared one scroll position and one component.
- Decision: **four routes — `/ledger`, `/import`, `/slips`, `/recovery` — and `/` redirects to `/ledger`.** One canonical URL per surface, so nothing has to be kept in step, and the ledger is what an ordinary day opens on. `app/ledger-app.tsx` split into `app/import-bench.tsx` (select → unlock → bind → review → the `.pldemo` preview) and `app/recovery-bench.tsx` (export and restore); the transactions view and slip capture were already components and moved unchanged.
- Decision: **the shell owns the header, nav, footer and the session control**, in `app/site-header.tsx`. The development sign-in used to live inside "Import / 01", which was never true of it — a session is not a property of the import bench, and when OAuth lands it belongs in exactly the place this now is.
- **The session line is a polite live region, not a second `role="status"`.** Every route already has one status line, and adding a second to the shell would make `getByRole("status")` resolve to two elements on every page — breaking assertions in specs that have nothing to do with the header. Deliberate, and the kind of thing that is only cheap to decide before the shell exists.
- Decision: **no state crosses a route.** The one piece that did was `backupStale`, which the import bench set and the recovery band read. Splitting it revealed the coupling was wrong anyway: it made a *synthetic preview* go stale because a *real ledger* was exported. The import route now tracks only its own preview, and the confirmation message points at Recovery in words. Nothing is lost, because the authoritative staleness check is the snapshot sequence `confirm_backup_custody` compares server-side — the flag was always a hint.
- Decision: **service-worker registration moves from the capture form to the shell**, and this one is a privacy argument rather than a tidiness one. A Web Share Target POST can only be kept on the device by a worker that is *already* registered. With one page, any visit armed it; with four, a worker installed only by `/slips` would let the first share ever made reach the server's fallback handler — which is precisely what D-050 forbids. It remains exactly one registration site, and the worker still caches nothing but the shared image. The share redirect and the manifest's `start_url` were retargeted to `/slips` and `/ledger` accordingly.
- Consequence: the `section-index` ordinals ("Ledger / 05", "Slips / 06") named a position on a page that no longer exists, so single-section routes carry the label alone; the import flow keeps 01/02/03 because there the numbers are stages.

## D-062 — A captured slip belongs in the ledger view, as a provisional entry that stays out of every confirmed figure

- Date: 2026-07-31
- Status: Accepted and built, at the owner's direction. Supersedes the read-side assumption in D-050/D-056 — that slips would stay invisible until reconciliation (task 22) gave them a meaning — while leaving every write-side decision in those entries untouched.
- **How it was found, which is the pattern by now:** the owner captured a real slip through the UI, opened the ledger, and it was not there. The capture had worked — `public.slips` held the row. Nothing in the app displayed it, and `GET /api/v1/slips` had existed since migration 011 **with no caller at all**. Task 20 shipped a write path with no read path, and every test passed because each one asserted against the database directly.
- His stated intention, which the build had quietly narrowed: *slips should show in the ledger and be verified against the statement once in a while.* That is a strictly better product than "slips are invisible until task 22", and nothing in the invariants forbids it — the invariant is that `public.source_transactions` is written only by a confirmed import, not that a *view* may show one kind of row.
- Decision: **the ledger view renders one sequence of two kinds.** `LedgerEntry` is a discriminated union of a confirmed transaction and a captured slip; the same date/time/id comparator orders both, so a slip sits where it happened. The owner reads "what happened, in order", and a slip waiting for its statement happened.
- **Decision: provisional money is totalled separately and never folded in.** This is the load-bearing one. A slip and the statement row for the same payment are two records of one transaction, and until reconciliation matches them nothing can tell that they are a pair — so one combined total would overstate spending by exactly the amount of every slip that was captured *correctly*. Two true numbers beat one wrong one. The row count, deposits, withdrawals and net movement remain the statement's figures; provisional slips get their own line saying why they are apart.
- Decision: **a provisional row has no balance, in either money column.** A printed balance is the bank's statement of the account after a row; a slip is not in that chain, and deriving a figure there would invent one. Both cells read `—`.
- Decision: **slips appear in the all-accounts view only.** A slip carries no account by design — its QR names a bank, and only the statement says which of that bank's accounts the money moved through (D-056) — so filing one under a selected account would be the parser-guesses-the-binding mistake wearing different clothes. Selecting one account hides them and says that, rather than letting them silently vanish.
- Decision: a failure to load slips reports beside the rows instead of replacing them. The confirmed ledger is the authority and must not be hidden by an outage in the provisional half.
- Consequence: the section heading is now `Transactions` rather than `Confirmed transactions`, because it no longer shows only confirmed ones.
- Consequence, and worth stating: this makes the **missing correction path** visible. A capture is append-only with no way to fix a mistyped amount (task 20's recorded limitation), and until now that was invisible too. Seeing a wrong provisional row and being unable to correct it is the next thing the owner will hit.
- What this does **not** do: it does not reconcile. A slip whose statement has already been imported now appears twice — once provisional, once confirmed — and the app cannot tell. That is task 22, and this entry is what makes the pair visible enough to reconcile.
- Evidence: `lib/slips.ts` (`capturedSlipSchema`, `slipListSchema`), `lib/transactions.ts` (`LedgerEntry`, `toLedgerEntries`, `compareEntries`, `summarizeSlips`, `matchesSlipQuery`), `app/transactions-view.tsx`, `app/globals.css`, `tests/transactions.test.ts` (8 new tests: interleaved ordering, nulls-last on an untimed slip, totals kept apart, balances untouched, exactness past 2^53, filtering, and the strict wire contract), `tests/e2e/owner-session.spec.ts` (a slip captured then read back beside four confirmed rows, asserting the strip still counts 4, both balance cells read `—`, and one-account mode hides it). Gate on 2026-07-31: ESLint, `tsc --noEmit`, Vitest **259 passed / 7 skipped across 18 files**, production build, Playwright owner **17/17** and isolated **18/18**. pgTAP unchanged at 129/129 — no migration was needed, because the endpoint and the table were already there.
- **Superseded within the hour by D-063**, on the owner's direction, in the two places it hedged: slips are now counted in the totals, and a matched pair is one row rather than two. The reason it hedged — that nothing knew which records were pairs — was true when written and stopped being true when matching was built. The read-side decisions it took that still stand: slips belong in the ledger view, a provisional row carries no balance, and the difference between the bank's record and the owner's is stated in words rather than by colour.

## D-063 — Slips are reconciled against statement rows, so the ledger shows one row per payment and one total

- Date: 2026-08-01
- Status: Accepted and built, at the owner's direction, with both open choices put to him and answered. First half of `PLAN.md` task 22. **Read-time only so far** — the owner's overrides and the undo are the second half, and are not built.
- Context: D-062 put slips in the ledger but kept their money out of the totals, because a slip and its statement row would otherwise be counted twice. The owner's answer was that the totals should include them, that a payment should appear once, and that each row should say which records it rests on. That is reconciliation, and it was already task 22.
- **The fact that shapes everything here: there is no identifier to join on.** No supported layout prints the transaction reference the slip QR carries — Krungthai and KBANK print none, and SCB's is a short channel code such as `SIPI`. Checked in the layout descriptors before any of this was designed. So a match can only be inferred from bank, amount and date, and must therefore be visible, reversible, and willing to refuse.
- Decision: **match on bank, amount equal to the minor unit, and a date within three days; consider only the candidates nearest in date; and pair only when that is mutually unique** — the slip has exactly one nearest candidate row and that row has exactly one slip nearest to it. No tolerance on money, ever. The mutual-uniqueness clause is what makes the result independent of the order rows arrive in; a greedy matcher would pair two identical transfers with whichever came first and look confident doing it.
- **The nearest-date clause was added on measurement, not taste, and the measurement is the most useful thing in this entry.** Over the owner's real ledger — 1,465 rows, read directly after he widened the read grant to cover slips and statements — the share of rows sharing a bank and an exact amount with another row is **6.5% on the same day, 11.5% within one day, 16.3% within three, and 27.8% within seven**. The window that buys tolerance for a late posting therefore also doubles the ambiguity it must resolve. Restricting to the nearest date takes 16.3% back to **6.5%**, the same-day floor: the tolerance becomes free, and the residue is irreducible — two identical payments on one day, where no date rule can help. Competition between *slips* for one row is resolved the same way, so a slip three days out cannot block one sitting on the row's own date.
- **Validated against real slips, not only fixtures.** Six real slips read across the four layouts were checked against the live ledger: three matched a single same-day row, two had no candidate at all (their statements are not imported), and one — a Krungthai payment — found **two identical same-day rows**. That last case is exactly the coin toss the mutual-uniqueness clause refuses, and it appeared in the first six slips looked at rather than in a contrived test.
- Decision (the owner's, from two offered): **a matched pair collapses onto the statement row**, which keeps the printed balance and the immutable source facts and takes the slip's counterparty as detail, labelled `(from slip)`. The alternative — showing the slip — was rejected because a slip has no printed balance, and a row with no balance puts a hole in the running-total column.
- Decision (the owner's): **match automatically when the rule is satisfied**, badged and reversible, rather than requiring a confirmation click per slip. The click would be the same judgement the rule already encodes, and ambiguity never auto-matches.
- Consequence, and the point of the whole change: **the totals can now include slips**, because a matched slip is not a row. Rows, deposits, withdrawals and net movement count every payment exactly once, and the row count discloses how many of them are still provisional.
- Decision: **four statuses, in words**: `Verified by slip`, `Awaiting statement`, `Needs review · several rows match`, `Statement only`. The owner asked for a status on rows with no slip too, so the fourth exists rather than being left as the absence of a badge.
- Decision: **a slip is shown against an account when the owner holds exactly one at that bank**, and against none when they hold two. This is not a reversal of D-056 — the QR still names only a bank — it is the observation that with one account at that bank there is no choice to make, so nothing is being guessed. Derived at read time, never stored: a stored account id would be a guess written down that a later statement could contradict silently.
- Decision: **reconciliation runs over the whole ledger, before any filter.** A match is a fact about two records, not about what is on screen — reconciling the filtered subset would let choosing an account or typing in the search box silently unmatch a pair and move the totals.
- **Superseded in part by D-067 (2026-08-05)**, which built the second half and corrected the storage design named below: it cannot be a column on `public.slips`, because migration 011 made that table append-only.
- **What is deliberately not built yet, and what it costs:** the owner cannot override a match. ## D-067 — The owner's say over a match is stored, and a statement row is something only one slip can claim

- Date: 2026-08-05
- Status: Accepted and built. Migration 012, the second half of `PLAN.md` task 22. D-063 held this back deliberately so the rule could be judged against real data before a migration made it expensive; that judgement happened (D-064, D-066) and the rule now rests on measurement, so this stores it.
- **The design the docs specified was impossible, and the docs disagreed with each other.** `PLAN.md` said the override needs "a column on `public.slips`". Migration 011 put `slips_immutable before update or delete` on that table, so **no** column on it can ever be updated, whatever it holds — the design would have failed on its first write, at run time rather than at design time. `GOTCHAS.md` had recorded exactly this on 2026-08-01 while the same half was being designed; PLAN was never corrected and the two sat in contradiction for four days. Both are now reconciled. **The lesson is about which document to believe:** GOTCHAS records what was discovered by reading the schema, PLAN records what was intended, and where they disagree the schema wins.
- Decision: the established **`transaction_overlays` + `overlay_revisions` shape**, not a new one. `public.slip_match_overlays` holds the current decision and is mutable with a revision counter; `public.slip_match_revisions` holds the history and is append-only under `private.reject_change()`. `public.set_slip_match` is the only write path, with `authenticated` holding no insert, update or delete on either table, and optimistic concurrency through an expected revision exactly as `update_transaction_overlay` does it. Inventing a second shape for a problem this ledger had already solved would have been the more expensive choice, not the cheaper one.
- Decision: **three states, one of them the absence of a row.** `matched` names the statement row, `unmatched` says this slip is none of them, and no row at all means no decision and the automatic rule applies — which is where every slip starts. The absent state is what keeps this additive: nothing changes for a ledger whose owner never disagrees with anything.
- **The guard nothing asked for, and the reason it exists.** A partial unique index on `(transaction_id, owner_id)` makes it unrepresentable for two slips to claim one statement row. `lib/slip-reconcile.ts` already enforces mutual uniqueness, but only as a property of a *proposal* recomputed on every read; a stored decision is a fact, and two facts claiming one row would double-count the very payment reconciliation exists to count exactly once. Partial because `unmatched` decisions all carry a null transaction and must not collide with each other. Red-proved: dropping the index fails exactly one contract of 24 and nothing else.
- **Decisions are applied before the rule runs, and the ordering is load-bearing.** The reader removes decided slips and claimed rows from the pool *first*, so the automatic rule only ever sees what is left. Layering decisions over the rule's output instead would let an automatic pairing consume the row the owner had already assigned, and the owner's explicit decision would then lose to a guess depending on iteration order — the same class of bug mutual uniqueness was introduced to kill.
- Decision: **a decision naming a row this ledger no longer holds is ignored, not obeyed.** A restore or a re-import can remove the statement row a decision pointed at. Obeying it would pair the slip with nothing and drop it out of the totals silently; ignoring it returns the slip to being its own visible provisional row. Fail visible, not fail quiet.
- **Decision, and the one most worth revisiting: a manual match is held to the same two facts the automatic rule uses** — same bank, and an amount equal to the minor unit. What the override buys is resolution of *ambiguity* and rejection of a *wrong* pairing, which are precisely the two gaps D-063 recorded. It is not a way to declare that two unrelated sums are the same payment. The reason is asymmetric harm: a refused override costs the owner a manual entry, while an accepted mismatched pairing **collapses two records into one row and takes a real payment off the ledger**, with no audit row that makes the loss visible afterwards. This is the conservative end and the reversible one; loosening it later is a decision to write down, not a default to drift into.
- Consequence: **backup schema v4**, with v2 **and** v3 still restorable. Each version keeps its own kind list rather than the newest list being applied leniently to all, so a v3 manifest does not pass as v4 and a v2 payload carrying a `slips` key is still refused — widening the union is not the same as relaxing it. The reason v2 must keep working has not changed since D-056: the only backup covering this ledger whole is still a v2 file (D-065 re-verified it at sequence 19).
- **Deliberately not built, and named so it is not mistaken for done:** `set_slip_match` has no HTTP route and no UI, so the decision cannot yet be made from the app. That is the next step. It is called out because it is the exact shape of D-063's origin — task 20 shipped a write path with no read path, and it took the owner opening the ledger and finding nothing to notice.
- Evidence: `supabase/migrations/202608050012_slip_match_decisions.sql`, `supabase/tests/005_slip_match.sql` (24 contracts: least privilege on both tables, RLS forced, the revision counter, the audit event, the mutation-sequence bump, optimistic-concurrency conflict, undo, the decision vocabulary and the null that must travel with it, the bank and amount guards, unowned slip and unowned transaction, the double-claim refusal, append-only history under both `update` and `delete`, and the aal1 refusal last so nothing above runs on a downgraded session), `lib/slip-reconcile.ts` and `tests/slip-reconcile.test.ts` (7 new), `lib/backup-contract.ts` and `tests/backup.test.ts`. ## D-087 — OCR locates the amount and the owner reads it, so no machine-read digit enters the ledger

- Date: 2026-08-10
- Status: Accepted, the owner's decision after the measurement below; policy layer and asset plumbing built, the browser module and the capture-form UI are not. Advances `PLAN.md` task 21 and settles the engine question that had been open since 2026-08-01.
- **The measurement that decided it**, run 2026-08-10 over all 23 real samples in `receipts_sample/` with a throwaway harness under `.runtime/` since deleted. Three findings, all recorded in `docs/SLIP_CONTRACT.md`:
  - **The ceiling is the Thai label, and no language choice moves it.** Best outcome per image at native resolution: Thai-only `OK=13 LABEL_NOT_FOUND=7 VALUE_NOT_MONEY=2 VALUE_AMBIGUOUS=1`; with English `OK=15 LABEL_NOT_FOUND=7 VALUE_AMBIGUOUS=1`. `LABEL_NOT_FOUND=7` is identical either way — English helps the *figure*, which is Latin digits, and cannot help a label it never recognises. So the realistic reading ceiling is **15 of 23 (~65%)**, on a larger and less flattering denominator than D-066's 11 of 14; the two are not comparable and neither is a regression on the other.
  - **The QR retry ladder does not transfer, and upscaling makes OCR worse.** Thai-only reads 13 at native and 11 at 2×; of 10 failures, a 2× cubic upscale recovered 1 and **broke 3 that were working**. That is the opposite of D-053, and the reason is that the two are different problems — a QR decoder needs module size above a threshold, a text recogniser needs glyph shapes near its training, and interpolation adds no information while disturbing them. **`lib/slip-scan.ts`'s ladder must not be reused here.**
  - **Digits are unstable about one time in fifteen.** Of 14 images read by more than one configuration, 13 agreed and 1 did not — so at least one configuration returned a figure that **passed the money grammar and was wrong**. What was measured is stability, not correctness; establishing accuracy needs every amount read by eye, which was not done, so no accuracy rate should be quoted from this.
- **Decision: ship the engine to *locate* the amount, and show a cropped enlargement beside the field instead of pre-filling it.** `locateAmount` returns the region spanning the label and its value; the owner reads the digits. **No machine-read digit reaches a stored value**, so the 1-in-15 instability cannot become a wrong amount in the ledger at all — the risk is removed rather than mitigated.
- **Why this is not the weaker option it sounds like.** It answers a strictly easier question, so it covers **more** slips than reading would: the label was found on 16–17 of 23 while the amount parsed on 13–15, and the extra images are exactly the ones where reading failed for digit reasons — which are the ones a person most needs enlarged. It also solves the actual pain, which is reading a slip on the same phone being typed into, rather than the imagined one.
- **Decision: Thai only.** English costs ~5 MB and buys two slips in twenty-three, and under a crop-and-read design those two are read off the crop regardless. Measured on disk as shipped: `tha.traineddata.gz` 904,570 bytes, `tesseract-core-simd-lstm.wasm` 2,857,601, worker and core loader the rest — **3,962,749 bytes total**, against `public/zxing_reader.wasm`'s 1,065,866. `PLAN.md`'s longstanding "roughly 10–15 MB" estimate was too high for Thai-only and about right for both languages.
- **Assets are self-hosted and copied at build time, never committed and never fetched from a CDN.** `connect-src` names `'self'` and the configured Supabase origin alone (D-058), so a CDN fetch is blocked by policy — and a finance app pulling executable code and a language model from a third party at runtime would have handed that party the page. `scripts/copy-tesseract-assets.mjs` runs from `prebuild` beside the ZXing copy, so the version match is structural rather than remembered.

## D-097 — New owner data goes in a new table, never a new column, so every backup version stays cheap to keep

- Date: 2026-08-12
- Status: **Decided by the owner and enforced by a test**, not by a note. It settles the question D-090 left open before task 27's migration is written, which is what D-090 asked for.
- **The rule.** New owner data gets a **new table**. A new column on an existing table is not allowed without reopening this decision. `SPEC.md` gate 6's promise — a version the owner still holds a backup in stays restorable — is kept in full.
- **The question came from task 27**, which needs a table for LINE cards and therefore moves the backup version. D-090 had recorded the neighbouring question as unresolved: `export_backup_snapshot` serialises whole rows with `to_jsonb`, so a new column travels in the file whether or not the version changes, and "what that costs a restore into an older ledger has not been worked out".
- **Reading the code made the question sharper than D-090's framing.** The cost is not paid by an old restore; it is paid immediately by the current export. Every row schema in `lib/backup-contract.ts` is `.strict()`, so the moment a migration adds a column, the export emits rows carrying an extra key and **the reader refuses its own freshly written file**. The backup stops working that afternoon, not on some future restore. That is the good failure — loud, not silent — but it means a column is never a deferrable decision.
- **The trap is the obvious fix, not the failure.** Adding the key to the row schema repairs the current version and silently breaks v2, v3 and v4, because all four versions deliberately share one row schema per table. Repairing *that* properly means per-version row shapes, which breaks the additive chain (`v3 = {...v2, slips}`), then the chunk union — which is keyed on table name and knows nothing about versions — and then `restore_backup`, which handles four versions in one function. One column, three layers, and the cost multiplies with every later version.
- **Two alternatives were weighed and rejected.** Keeping the promise *and* permitting columns is the combinatorial case just described. Dropping the promise to only the current version was rejected on a cost argument rather than a safety one: an old file is not worthless without it — the migration history is in the repository, so an old ledger can be rebuilt and restored into — but the path stops being *tested*, turning recovery into archaeology at the worst possible moment. And it costs work to delete a guarantee that currently costs nothing to keep, since the additive chain does not get more complex when a table is added.
- **Enforced by two tests in `tests/backup.test.ts`, deliberately structural rather than fixture-based** so they cannot rot as row contracts change: every table carried by more than one version must resolve to the *same* row schema object, by reference; and each version's table list must begin with the previous version's, so growth can only append. **Red proof:** giving v5 a look-alike `accounts` row schema with one extra key fails exactly one test of the ten in that file, reporting `accounts diverges at v5`.
- **Consequence for task 25, and it reverses a preference.** D-090 proposed carrying categorisation provenance as a column on `transaction_overlays` and called it "the cheaper of the two shapes". Against this rule it is the expensive one: provenance needs its own table. That is one extra join and one more table in the backup, and it costs nothing else.
- **Consequence for task 27: none.** It adds a table and no columns, so it is unaffected and remains buildable as scoped.
- Evidence: `lib/backup-contract.ts` (row schemas, the v2→v5 chain, `backupChunkSchema`, `restoreActionSchemas`), `supabase/migrations/202608090013_cash_entries_and_corrections.sql` (`export_backup_snapshot`), `tests/backup.test.ts` **10 passed**, up from 8. `PLAN.md` tasks 25 and 27, `SPEC.md` gate 6.

## D-098 — A notification card is its own record, identified by a computed fingerprint the balance makes unique

- Date: 2026-08-12
- Status: **Built and verified** against the synthetic project. This is `PLAN.md` task 27's migration — the database half. Capture, the reading of a screenshot, and the ledger view are not built, and the task is not done.
- **What landed.** Migration 016 adds `public.notification_cards`, `private.notification_card_fingerprint`, `public.capture_notification_card`, and moves the backup **v5 → v6 with 2, 3, 4 and 5 staying restorable**. One table and no new column, which is D-097's rule holding on the first case that tested it.
- **Why the version move is in the same migration rather than a follow-up.** `export_backup_snapshot` serialises whole rows with `to_jsonb`, so the moment the table exists the export must carry it or the backup silently stops covering every owner table and `SPEC.md` gate 6 is broken. There is no window in which the table can exist and the version cannot move.
- **Identity is a fingerprint, and it is weaker than a slip's on purpose.** A card carries no reference and no QR, so `unique (owner_id, bank_code, slip_reference)` has no counterpart. The precedent is the statement importer, which faces the same absence and answers it with `private.row_fingerprint`; this is that shape over account, channel, kind, amount, date, time and balance. **Record what it is not:** a fingerprint is idempotent, not tamper-evident. It is computed **in the database from the stored facts and never accepted from a caller** — stronger than `confirm_import`, which recomputes a digest the client also computes, because a card has no client-side dedup step to need one.
- **The balance is what makes the key work, and that is the measured finding rather than a hope.** Two payments of the same amount at the same minute on one account are indistinguishable without it, and D-063 measured 16.3% of rows sharing a bank and exact amount with another within three days. **Red proof:** dropping `balance` from the fingerprint input fails exactly one test of the 26 in `supabase/tests/007_notification_cards.sql` — `the same amount at the same minute on a different balance is a distinct card` — and nothing else. The symptom that failure describes is the real one: a second payment swallowed as a re-capture, with no row and no error.
- **The card is bound to an account and the channel is checked against that account's bank.** A slip carries no account because its QR names only a bank; a card names an account and prints that account's running balance, which is meaningless unbound. The per-layout digit rule (`lib/notification-card.ts`) narrows the candidates and this refuses the pairing outright when the bank disagrees — without it an SCB card could bind to a KBANK account whose stored last four happened to match.
- **What is deliberately absent, and what each would cost.** A card has **no correction overlay and no stored match decision**. Both are wanted and the slip path grew both, in migrations 013 and 012 — but neither is designed, and each needs its own table and therefore its own version bump. Building undesigned tables now to save that bump is the wrong trade: D-097 established that appending a table does not compound the cost. Recorded as a limitation, exactly as migration 011 recorded the slip correction it left out.
- **The version pair that matters next is proven before anything depends on it.** The owner's newest file is the **v5** export from the hosted project, and pushing this migration there makes that project v6 — so the next recovery is a v5-into-v6 restore. `tests/recovery-portability.test.ts` now runs it end to end into a separately bound project: an older file in, the current contract out, every owner and actor rebound, and the card table present and empty rather than invented. That is the same argument D-089 made for v4-into-v5, made before the need rather than after.
- Evidence: `supabase/migrations/202608120016_notification_cards.sql`, `lib/backup-contract.ts`, `supabase/tests/007_notification_cards.sql` (**26 contracts**), `supabase/tests/002_security_contracts.sql` (export version 6 and the card table's presence in it), `tests/recovery-portability.test.ts` (three named lines, all checked), `tests/backup.test.ts`, `tests/helpers/local-owner.ts`. ## D-099 — A card is read from labels paired with its direction, and direction itself is read twice

- Date: 2026-08-12
- Status: **Decided from a measurement and enforced by tests.** The grammar is built; no reader, form or route consumes it yet. `PLAN.md` task 27.
- **What was measured.** All five screenshots in `receipts_sample/line/` were read structurally under a grant given the same day — three card screenshots carrying two cards each, plus the two in-app lists this task excludes, which re-confirmed the exclusion rather than being skipped. Shapes and label wordings only; `docs/NOTIFICATION_CARD_CONTRACT.md` records them and nothing read became a fixture, a quotation or a commit.
- **The rule: anchor on labels, and look the label up per layout *and* per direction.** Field order, label set and row count all differ between layouts and between the two directions of one layout. SCB Connect prints its amount above the labelled rows with no label at all; KBank Live labels it; Krungthai Connext uses the direction word itself as the label. Position-based reading cannot survive that, which is the third time this repository has met the lesson — D-024 and D-026 for statements, `docs/SLIP_CONTRACT.md` for slips.
- **The finding that forced "per direction" rather than "per layout".** On Krungthai Connext, `จากบัญชี` names **the owner's own account on an outgoing card and the sender's account on an incoming one**, and both print four digits with nothing marking which is which. A reader that matched the label alone would bind roughly half of that layout's cards to a counterparty's account or to none — the same silent shape as the KBank digit offset the owner caught, and undetectable without reading both directions of a real card.
- **Direction is read twice and refuses when the two disagree.** Every layout names its direction in words *and* signs its amount. Both are read; a contradiction returns a refusal naming both readings rather than trusting either. A card stored on the surviving signal is a payment recorded backwards, and `notification_cards` is append-only. This mirrors the statement readers taking direction from the balance chain and cross-checking it against column geometry (D-039). A zero movement is a refusal too: no card prints one, so a zero is a failed amount read wearing a plausible shape.
- **Thai has no word separator, and that turned a substring test into a defect.** KBank Live's incoming title `รายการเงินเข้า` **contains** Krungthai Connext's incoming word `เงินเข้า`. The first implementation used `String.includes` against the caller's layout alone, and Krungthai's grammar therefore read a KBank card happily — after which the account digits would have been matched with the wrong mask. The rule now compares against every layout's words, keeps only the longest reading of any nested pair, and refuses when the surviving word belongs to another channel. **Red proof:** removing the nesting filter fails exactly two tests of the 19 in `tests/notification-card.test.ts`, both of them the cases that read KBank's own wording, because the nested pair then looks like an ambiguity. The defect was found by a test written to assert the opposite, which is the argument for writing the cross-layout case at all.
- **A second clock exists and only one of them is the transaction.** The card prints its own timestamp; LINE prints a message timestamp outside the bubble, and on one measured KBank pair they differ. The card's is what equals the statement row's. Two layouts print their unlabelled field on the line under the title — SCB its amount, KBank its timestamp — so that position is a named anchor rather than "the unlabelled one", which would otherwise invite an unanchored search that finds LINE's clock.
- **The gap was named, the owner filled it, and filling it overturned two conclusions.** The first pass had only outgoing SCB cards, so `fieldMapFor` refused an incoming SCB Connect card rather than assuming its labels by analogy. Three more screenshots arrived the same day and proved that refusal right twice over: **SCB Connect carries the same `จากบัญชี` collision as Krungthai**, which two outgoing cards could never have shown; and **SCB Connect names a counterparty on incoming cards**, which retired the per-layout `carriesCounterparty` flag — whether the other side is named depends on direction and transfer type, not on the bank. Both had been recorded as settled by the first pass and both were wrong. Asking for the missing case cost one message and was worth more than any amount of reasoning from symmetry.
- **Counterparty anchors are ordered alternatives rather than one label**, because a single direction of a single layout has two measured variants: an outgoing Krungthai card to a bank account labels the recipient `ผู้รับโอน` and the account `ไปยังบัญชี`, while the same card to a wallet uses `ไปยัง` and `หมายเลข`. A reader keyed to one label reads one variant and silently misses the other. The lists are open rather than closed — two variants were found only because two transfer types happened to fall inside a twelve-card sample.
- **What the cross-layout check cannot do, stated so nothing relies on it.** SCB Connect and KBank Live print the **identical** incoming title, so no printed word distinguishes those two and the channel must come from the LINE conversation the screenshot was taken in. That limit is asserted by a test rather than left implicit.
- Evidence: `lib/notification-card.ts`, `tests/notification-card.test.ts` **22 passed**, up from 10; `docs/NOTIFICATION_CARD_CONTRACT.md`, measured over **twelve** real cards across two read passes on 2026-08-12. Vitest **443 passed / 7 skipped across 25 files**. `PLAN.md` task 27, D-098, D-031, D-039.

## D-102 — A card reconciles on its printed balance, which breaks the tie a slip cannot and refuses when it disagrees

- Date: 2026-08-13
- Status: **Built and green through the full gate.** **`PLAN.md` task 27 is complete**: the ledger view and the reconciliation were its last two parts, and both landed here. Adds no route, no RPC and no migration — it consumes the `GET /api/v1/notification-cards` that shipped with D-101 and closes the last of that route's two callers.
- Context: a captured card was stored and invisible. D-101 left the ledger view and the reconciliation as the whole of what remained, and the reconciliation is the interesting half — the balance measured equal to the statement row's on 6 of 6 real cards is what a slip has never had.
- **Decision 1: a card's rule is its own module, not the slip rule with a different record in it.** `lib/notification-card-reconcile.ts` matches on the **account** rather than the bank — `POST /api/v1/notification-cards` already checked the printed digits resolve to it (D-101), so `account_id` is a checked fact where `slipAccount` can only guess and returns null whenever the owner holds two accounts at one bank — then on the exact amount, then a one-day window, and then on the printed balance.
- **Decision 2: the balance does two jobs and they are kept apart, because one makes matches and the other refuses them.** As a **tie-breaker** it resolves the case `proposeSlipMatches` refuses outright as a coin toss — D-063 measured 16.3% of this ledger's rows sharing a bank and exact amount with another within three days, and two rows never share a running balance. - **Decision 3: the balance is not identity, and the limit is carried into the code rather than left in a document.** n is 6, both cards in each screenshot share an account and a day, and none was captured while a hold was outstanding — two layouts print an *available* balance and the third a *remaining* one, and those diverge at many banks exactly when a hold exists. The cost of that limit being wrong is a correct pairing refused, which is visible; treating it as identity would buy a wrong pairing accepted, which is not.
- **Decision 4: a card does not compete with a slip for a statement row, and the two rules are deliberately independent.** One payment can produce both an e-slip and a LINE push, so the two records are not rivals for a scarce row — they are two pieces of evidence for one movement, and a row is allowed to carry both. - **Decision 5: `balance-conflict` is a row status of its own, not folded into `needs-review`.** They ask the owner for different things: "several rows could be this" is an ambiguity to resolve, while "the balance contradicts every row that otherwise fits" is a figure to check. Only a card can reach it, because only a card prints a balance to contradict anything with. The other three card states reuse the slip names — a status describes a record's relationship to the statement, not which kind of record it is, so the Status control asks one question rather than two.
- **Decision 6: an unmatched card is counted apart from `provisional` and from `cash`, and its row prints its balance where a slip and a cash entry both print a dash.** A slip is a third party's receipt and a cash entry is the owner's own typing; a card is the **bank's** record, pushed at the moment of the transaction, so an unmatched card is good evidence that has not met its statement row yet. Its printed balance is the same figure the statement prints in its balance column, so it is shown — marked *as printed*, because it has not been confirmed against a row. The all-accounts column stays a dash: that figure is walked from statement rows only.
- **Decision 7: a card's match cannot be overruled and the view says so in words.** A card has no match-decision table and no correction overlay — `PLAN.md` task 27 keeps both for one migration rather than one backup-version bump each. So the row states plainly that the pairing is recomputed on every load and that neither an override nor a correction exists yet, rather than leaving the owner to notice a button that is not there.
- **A defect the browser spec caught that no unit test could.** A counterparty read off a card was labelled `(from slip)` on the collapsed row — the suffix was written when a slip was the only record that could supply one. It named a record that is not on the row, and the two are corrected in different places. Now attributed to whichever record it came from.

The *ledger view* has no such dependency, so two specs now drive it end to end — the card is posted through its real route under the browser's own signed-in session, which exercises every check the route makes including the per-layout account binding.

## D-103 — A card's balance disagreement may be overruled and the consent is stored, and a wrong card is retired rather than re-bound

- Date: 2026-08-13
- Status: **Designed, not built.** Scopes `PLAN.md` task 29 (migration 017, backup v6 → v7). Recorded before any SQL so the two owner decisions below are not re-derived or re-litigated when it is built. Task 27 is complete and this does not re-open it.
- Context: D-102 finished task 27 and deliberately left a card with no correction overlay and no stored match decision, each needing its own table and therefore its own backup version bump. Designing them together is what makes them one migration rather than two.
- **Decision 1 (the owner's): a balance disagreement may be overruled, and the overrule is recorded.** D-102 made the balance a fail-closed cross-check — a card contradicting every row that otherwise fits refuses to pair. The question was whether the owner may then say "it is that row anyway". **He may.** The reasoning is D-067's: an override exists precisely to reach past what the rule refused, and a rule that only ever offered what it had already found could resolve nothing. Here it is sharper than for a slip, because a **legitimate** disagreement is a known and measured possibility rather than a hypothetical — two layouts print an *available* balance and the third a *remaining* one, and those diverge exactly when a hold is outstanding, a case never observed for these accounts (`docs/NOTIFICATION_CARD_CONTRACT.md`). Refusing outright would leave a correct pairing unrecordable, and the only workaround would be editing a figure the owner had read correctly off the screen — which is worse than the disagreement.
- **Consequence: the RPC stores the consent, not a computed flag.** It compares the card's **corrected** balance with the row's printed balance and refuses unless the request carries an explicit acknowledgement; that acknowledgement is what is stored. A flag saying "these disagreed" would be re-derivable at read time and would **go stale the moment the balance is corrected**; a record saying "the owner accepted a mismatch" is a fact about a decision and never does. Same shape as migration 012 storing the owner's disagreement with the rule rather than the rule's own output.
- **Decision 2 (the owner's): a card captured wrongly is retired, not re-bound.** Presented as a choice between making `account_id` correctable, retiring the card, both, or neither. **Retirement.** It is one mechanism covering two failure modes rather than one covering each: a wrong account binding *and* a second capture that typed something differently and therefore landed as its own row. Making the account correctable would fix only the first, would leave a duplicate in the totals forever, and would contradict a refusal the capture form already shows the owner — D-101 says in words that a captured card cannot be re-bound.
- **Consequence: retirement is a third decision value, not a fourth table.** `not-a-payment` beside `matched` and `unmatched`, so one place answers what a card's relationship to the ledger is. **It is reversible while the card row is not**: a decision is an overlay carrying a revision, so a card retired by mistake is un-retired by changing the decision — which is the append-only table's guarantee kept intact rather than worked around.
- **What surfaced the second decision, and it was not in the original scope.** Nothing in any migration can retire any record: no slip, no cash entry and no card can be withdrawn once captured, so every one counts in the ledger totals forever. Checked across all sixteen migrations rather than assumed. It rarely bites a slip, whose identity comes from a CRC-checked QR and which is therefore seldom junk. A card is typed by hand from a screenshot, so a wrong one is a likelier accident — and **D-102's ledger view is what made it visible**, which is the argument for shipping a read surface before designing the write ones that correct it.
- **What is deliberately not correctable, recorded so the reasoning is not re-opened**: `account_id`, `channel` and `printed_account_digits`. The binding was checked against the printed digits under that layout's mask at capture and that check cannot be re-made after the fact; the channel and the digits are what it was made against, so all three travel together. Every other field the owner typed is correctable, the balance included.
- **One consequence that needs no new mechanism.** The fingerprint covers the account, so re-capturing the same screenshot against the *right* account yields a different fingerprint and a new row. Re-capturing the identical thing hits the retired row and returns `captured: false` exactly as today; the route says it is already held and retired. Nothing about retirement changes `capture_notification_card`.
- Evidence: `PLAN.md` task 29 carries the table-by-table design. Precedents copied rather than invented: `supabase/migrations/202608050012_slip_match_decisions.sql` (overlay, optimistic revision, partial unique index, append-only revisions) and `supabase/migrations/202608090013_cash_entries_and_corrections.sql` (nullable column per corrected field). ## D-106 — `anon` holds `TRUNCATE` on every table added since migration 002, and a grep of the migrations is what hid it

- Date: 2026-08-15
- Status: **Measured on the synthetic project, not yet fixed.** Corrects one conclusion in **D-105**, which stands otherwise. `PLAN.md` task 31 carries the remedy, which needs its own migration.
- **What D-105 got wrong.** It asked whether a blanket grant could silently expose a table added by migration 017, searched every migration for `alter default privileges`, found none, and concluded that a new table "starts with no privileges and holds exactly what its own migration gives it". **That is a conclusion about the database drawn from a search of the repository, and it is false.** The measurement came later, while red-proofing task 30's new assertions, and the measurement wins.
- **What is actually true.** Supabase's own bootstrap — not this repository — sets `alter default privileges in schema public` granting `Dxtm` (`truncate`, `references`, `trigger`, `maintain`) to `anon`, `authenticated` and `service_role` on every future table created by `postgres`. Migration 002 cleans that up with `revoke all on all tables in schema public from anon, authenticated`, but that form expands **at execution time** over the tables then existing. **No migration after 002 repeats it.** So every table added since keeps the default set: thirteen tables — all of `slips`, `slip_match_*`, `slip_correction_*`, `cash_entr*`, `notification_cards` and the four from migration 017 — carry `TRUNCATE` for `anon`.
- **The later migrations' revokes are no-ops, which is the part most worth not re-deriving.** Migrations 011 through 017 each write `revoke insert, update, delete ... from authenticated, anon`. The default privileges never granted `insert`, `update` or `delete`, so those statements remove nothing. The protection against writes is real but comes from those privileges never having been granted, not from the revoke that appears to provide it. A reader checking that a new table is locked down will find a reassuring line that did nothing.
- **Severity, stated precisely rather than dramatically.** `TRUNCATE` **bypasses RLS** — row-level policies are not consulted for it — so the privilege would empty a ledger table outright. It is **not reachable from the internet today**: PostgREST maps no HTTP verb to `TRUNCATE`, this repository exposes no SQL-executing RPC, and the publishable key is a PostgREST JWT rather than a database credential, so holding it does not let anyone open a session as the `anon` **database** role. This is a defense-in-depth gap and a latent one, not a live hole. It becomes live the moment anything ever runs caller-influenced SQL as `anon`.
- **How it was confirmed**, because a privilege listing is not proof of what a role can do: `begin; set local role anon; truncate public.notification_card_decision_revisions;` **succeeded**, and the transaction was rolled back. Verified on `private-ledger-local`, the synthetic and disposable project. **Not checked on the hosted project** — the standing read grant there covers counts and migration versions only, and a privilege audit is neither, so it was not run. It is very likely identical, since the same bootstrap and the same migrations produced it, but "likely" is exactly the word D-105 should have used and did not.
- Consequence: **task 30's `anon` assertion deliberately excludes `truncate`.** Including it would make the suite red against a real gap that a test cannot close, so the assertion states what is true today, its title says "no read or write privilege" rather than "no privilege of any kind", and a comment beside it names the gap and points here. Widening it to `truncate` belongs in the same change that revokes it.
- **The general lesson, and it is the second one this week about asserting from text.** `SPEC.md`'s stale backup version (D-105) was a number in prose contradicting the source that owned it. This is the same shape one level down: a property of the running database inferred from the files that are supposed to produce it. A grant question is a database question. The repository is evidence about intent; only the database is evidence about state.
- Evidence: `supabase/migrations/202607240002_security_and_rpcs.sql` line 86 (the `revoke all` that reaches only what already existed), `supabase/tests/008_notification_card_decisions.sql` (task 30's three new assertions, 250 pgTAP tests across 8 files with a two-part red proof), `information_schema.role_table_grants` and `pg_default_acl` on `private-ledger-local`. ## D-107 — Migration 018 takes back the inherited default privileges and stops the next table inheriting them

- Date: 2026-08-15
- Status: **Built and green, applied to `private-ledger-local` and `private-ledger-recovery`.** Closes `PLAN.md` task 31 and the gap D-106 measured. **Nothing hosted was touched**: the hosted project is now **three** migrations behind, not two.

## D-113 — Repairing a card's punctuation without touching a digit is what makes a pre-fill viable, and the guard is the design

- Date: 2026-08-16
- Status: **Measured. Still not decided.** Extends D-112 with a better instrument; D-087 stands until the owner changes it. Nothing in the application was touched — every number here comes from a throwaway harness.
- **Why the instrument had to improve.** D-112's harness printed a joined string per field and left **nineteen judgements to a human eye**, which is the manual step that goes wrong quietly. The second version does what a pre-fill would do — pull the candidate token, run it through the app's own `parseThb` — and prints the counts directly. It immediately contradicted the hand reading on the field that mattered least and the field that mattered most: the amount was **14** of 19 rather than the 13 counted by eye, and **the date was 0 of 19**, where the hand reading had called the separators cosmetic.
- **The date result is what forced the idea.** `/` comes back as `|` or `!` on essentially every card, so under a strict grammar **no card's date would ever be offered**. That is not a marginal loss; it is one of the four fields a card stores.
- **Decision: repair characters that carry no value, and prove that is all that happened.** `|` and `!` become `/`; a leading `=`, `~`, en dash or em dash becomes `-`; a thousands comma with a stray space is rejoined. **Then the digit sequence before and after is compared, and if it changed the repair is discarded and the original token stands.** The guard is the load-bearing part rather than the substitution list: it means a carelessly added confusion class in future still cannot alter a number.
- **Why this is not the lenient parser D-112 warns against**, which is the distinction the whole entry turns on. A separator and a sign character are not digits. Reshaping `=15.00` into a *different figure* is the silent error to fear; turning `=` into `-` restores a character that carries direction, and **direction is read twice** — from the card's words and from the amount's sign — with `readDirection` refusing when the two disagree. A repaired sign is therefore cross-checked by an independent signal rather than trusted. Nothing here softens `parseThb`, which still runs unchanged on the magnitude.
- **The result, on 10 images and 19 cards with no layout ambiguity**: amount **14 → 17 of 19 (89%)**, date and time **0 → 10 of 19 (53%)**, balance **15 of 19 with zero refusals** among those located, own account **11 of 19**. Every surviving refusal is an honest one and is named: two amounts with no digits in the region at all, two cards with neither date nor time, two account fields yielding five digits because the mask character read as one.
- **What this still does not establish**, and the limit is unchanged from D-112: whether an *accepted* figure is **correct**. That needs the card, and the card is the owner's to read. The harness writes accepted values to a gitignored local file for marking and does not grade itself, because an agent scoring its own OCR against its own OCR is measuring stability — the error that made this whole line of work necessary.
- **Three smaller instrument faults were fixed with it**, each of which had been silently degrading a number: the `located-but-empty` counter tested for an empty string and so read 0 while three regions held Thai text and no figure; only the amount was being judged, where a card stores four digit-bearing fields; and the layout was chosen as "whichever finds the most cards" with **no report when two tied**, which on a mis-assignment would put every field box in the wrong place and flag nothing. Ties are now counted and were **zero** across all ten images.
- **The shape a pre-fill would take, if the owner decides for it.** Repair, then the existing strict grammar, then **blank on failure** — never a guess. On this sample that fills the amount on 17 of 19 and refuses the rest, and it cannot offer a figure whose digits the engine did not actually read.
- Evidence: `.runtime/card-ocr-accuracy.harness.ts` and `.runtime/vitest.harness.config.ts`, both throwaway and gitignored and to be deleted; `lib/money.ts` (`parseThb`, unchanged and unsoftened), `lib/notification-card.ts` (`readDirection`, the second signal the sign repair relies on). D-087, D-112, `PLAN.md` task 33.

- **The one field.** `S__18636806_0.jpg`, card 2, Krungthai Connext, incoming: `occurredAt` refuses as `LABEL_NOT_FOUND`. One card of 25 — every other Krungthai card on the same samples finds the same label without trouble.
- **The cause, to the code point.** The label is `วันที่ทำรายการ`. `normalise` applies NFKC, which gives `ำ` (U+0E33) its compatibility decomposition, so the label the matcher compares against holds `ท` + **U+0E4D** (nikhahit, the small circle above) + `า`. On this card Vision returns **U+0E48** (mai ek, the small stroke above) in that position. The line matches the label's first **7** characters and diverges on the 8th. So the row was read and the *label* is unfindable — not the date.
- **It is the same class as D-117's SCB slash and not the same cause, which is what D-119 suspected and could not confirm.** Both are a character carrying **no value** being misread inside a label, which makes the whole field unfindable rather than misread. The slash case was `/` read as `|`; this is one superscript Thai mark read as another that looks like it at notification size. `repairSeparators` exists for exactly the first shape.
- **Why it was not repaired here and now.** A separator repair is safe because `/` and `|` carry nothing; a Thai tone mark **does** carry meaning in ordinary text, so a rule turning U+0E48 into U+0E4D is only safe *inside a comparison against a known label* and would need bounding as carefully as `opensWith` was (D-119). It would also fire on **1 card in 25**, so the measurement that justifies it barely has a subject — the same shape of thin evidence that made D-115's month-name reader worth building, measuring at 0 of 2, and deleting the same day. Recorded so the next attempt starts from the code point rather than from the symptom.
- **What a fix would have to prove**, whenever it is attempted: that no other label on any layout becomes findable-by-accident under the same repair, and that the repair is discarded when it changes anything but a mark — the digit-guard discipline of `repairToken`, applied to glyphs.
- Evidence: a throwaway harness under `.runtime/`, run once and deleted, which printed **no line** — only the label's code points, the count of characters shared, and the single differing character. ## D-122 — An empty list is sent as an absent key, because migration 019 refuses `[]` and fails hardest when the pre-fill is perfect

- Date: 2026-08-17
- Status: **Found in production by the owner's first real card read through Cloud Vision, reproduced in the database, and fixed in the app.** The database defect is real and stays open as `PLAN.md` task 37; nothing in this app can reach it any more.
- **The symptom.** The card form filled all four digit-bearing fields correctly from Vision, the owner changed none of them, and the capture was refused with `The record of what the card pre-filled is invalid, so nothing was captured.` The reader had worked perfectly; the record of the reading is what failed.
- **The cause, reproduced rather than reasoned about.** `private.assert_prefill_field_names` (migration 019) rejects a repeated field name by comparing `array_length(v_names, 1)` against `count(distinct n)`. **PostgreSQL answers NULL, not 0, for `array_length` of an empty array**, while the count answers 0 — so `NULL is distinct from 0` is true and an empty list raises `contains a repeated field name`. Run against the local project: an **absent** key returns an empty list, `["amount"]` returns one name, and **`[]` raises**.
- **Why it fires exactly when everything works.** The form always sent both keys. `prefillChanged` is empty precisely when the owner **changed nothing** — the outcome the whole trial is hoping for. At the local engine's 70% he was always changing something, so the case never arose; Vision at 99 of 100 made it the normal one. **A defect that only appears when the feature succeeds is the kind a gate does not find**, and this one had a full green gate over it.
- **Why no test caught it, which is the more useful half.** Both the pgTAP and route tests for "no pre-fill" **omit the keys**, and omitting takes an early return that never reaches the duplicate check. Nothing anywhere sent `[]`. The two encodings look interchangeable in the migration's own prose — "absent means an empty list" — and one of them was never exercised. **Two spellings of the same intent need two tests, or the untested one is where the defect lives.**
- **The fix, and why it is not a workaround.** `namesOrAbsent` in the card form sends an absent key for an empty list. Migration 019 *defines* absent as empty and `notificationCardCaptureSchema` already marks both keys optional, so this is the contract's own encoding rather than a way around it — the audit row records `[]` either way. It needs no migration, no backup and no ordering ceremony, which is what let it ship the same hour the owner hit it.
- **The database defect stays open deliberately, as `PLAN.md` task 37.** The one-line change is `coalesce(array_length(v_names, 1), 0)`. Writing it today would open a local/hosted migration gap and demand a fresh backup that goes stale the next time a card is captured, to close a hole nothing can reach. `tests/notification-card-routes.test.ts` **holds the current refusal in place with an explicit test that flips to 201 when 020 lands** — a test is the only kind of note that fails when it goes stale.
- **What this says about the adoption it followed.** D-120 argued the pre-fill guarantees were unaffected by the engine swap, and they were: no wrong figure reached a box. What the swap changed was *which paths get exercised*, and that is the thing to look for after any accuracy jump — the success path had never been walked end to end.
- Evidence: `app/notification-card-capture.tsx` (`namesOrAbsent`), `tests/privacy.test.ts`, `tests/notification-card-routes.test.ts`, `supabase/migrations/202608160019_notification_card_prefill_audit.sql` (`private.assert_prefill_field_names`). Reproduced with three one-line queries against `private-ledger-local`; no owner data was read or written. D-120, D-116, D-114. `PLAN.md` tasks 35 and 37.

## D-127 — A label survives one misread mark, proven safe by the labels staying distinct rather than by argument

- Date: 2026-08-18
- Status: **Built and measured.** The reader now offers **112 of 112** digit-bearing fields over the real screenshots, with **no refusals at all**. This reverses D-121's "recorded rather than repaired" on better reasoning, not on new evidence about the card.
- **The defect, to the code point.** `normalise` runs NFKC, which gives `ำ` its compatibility decomposition — so `วันที่ทำรายการ` is compared as fifteen characters with a bare **U+0E4D** (nikhahit, a small circle above) at index 7. On one real Krungthai card Vision reads **U+0E48** (mai ek, a small stroke above) there: the same small shape over the same consonant. The row is read correctly and the *label* becomes unfindable, so the whole field is refused. It is D-117's slash problem in a different character class.
- **What changed my mind, and it is a reasoning error worth naming.** D-121 refused the repair because "a Thai tone mark carries meaning where a slash does not". That is true of **general text** and this comparison is never made against general text — it is made against a **closed set of labels** written down in `lib/notification-card.ts`. I had applied a rule about prose to a lookup against a fixed vocabulary, which made a checkable question look like a judgement call.
- **So it became a check.** `labels are distinct under mark tolerance` enumerates every label in the **real** field maps, across both directions of all three layouts, and asserts no two of them differ only by marks above the line. If that ever fails the tolerance must go, and the test says so. **That is the difference between this and D-115's month-name reader**: that one was built on thin evidence about the world, and this one rests on a property of a table this repository owns.
- **Bounded three ways, and the bounds are the design.** Only characters that are **both** Thai marks *above* the line may differ (below-vowels U+0E38–U+0E3A are excluded, because the observed confusion is between shapes drawn above a consonant); **at most one** such substitution across a whole label; and lengths must still agree. A consonant, a digit or a below-vowel differing means a different row, however small the difference looks — both asserted.
- **The prefix check had to move with the completion check.** `labelAtLineStart` accumulates words and abandons a row as soon as it diverges. Relaxing only the completion test would have abandoned the row *at the misread mark* and never reached the relaxed test at all — so `labelStillPossible` is tolerant too. A half-applied tolerance would have looked correct and done nothing.
- **It cannot reach a value.** A label match says only where a field's value begins; every digit still passes `parseThb`, the digit guard and blank-on-failure downstream (D-114). The worst a wrong label match could do is aim a crop at the wrong row, which is what the distinctness proof rules out.
- **Measured through the shipped path**, not a copy of its arithmetic: over the real screenshots the reader now offers **amount, balance, timestamp and account digits at 28/28 each — 112 of 112, no refusal of any kind**, against 99 of 100 before. The sample has grown to 13 images and 28 cards as the owner captures more.
- **`MAX_MARK_SUBSTITUTIONS` is 1 and is not a tuning knob.** A second substitution has never been observed and each one multiplies the chance two labels meet in the middle. Raising it means re-running the distinctness proof, and the constant's comment says so.
