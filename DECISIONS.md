## D-012 — Import payload digest is server-recomputed and bound, never trusted

- Date: 2026-07-24
- Status: Accepted
- Decision: `confirm_import` recomputes the canonical payload digest in PostgreSQL over the statement frame plus the exact rows it receives (`private.sha256_jsonb` over `private.canonical_jsonb`), rejects any mismatch with the caller-supplied digest (`payload digest mismatch`), and uses the recomputed value as the stored/compared idempotency and audit anchor. The client (`app/api/v1/imports/confirm/route.ts` + `confirmationDigest` in `lib/canonical.ts`) computes the identical object — the frame scalars and the `rpcRows` (rows with server `fingerprint`/`sourceIndex` injected) — so the two digests agree byte-for-byte. This is server-authoritative: the caller digest is a verified claim, not the source of truth.
- Rationale: The prior digest was a trusted caller token used as the sole "same payload" discriminator, so materially different rows could be blessed under an unchanged claimed digest (the artifact-reuse path returned the original batch and silently discarded the divergent rows), and a fresh batch could persist rows whose recorded digest did not summarize them — corrupting the audit/backup/restore-equality chain. A digest that anchors idempotency and audit must be a function of the data it claims to summarize.
- Evidence: `supabase/migrations/202607240005_confirm_import_digest_binding.sql`, `supabase/tests/002_security_contracts.sql` (tamper test 19 fails before the fix, passes after), `lib/canonical.ts`, `app/api/v1/imports/confirm/route.ts`.

## D-013 — Restore manifest counts are canonical integers and the sequence range reserves increment headroom

- Date: 2026-07-25
- Status: Accepted
- Decision: `restore_backup` stage validation requires every `tableCounts[kind]` and descriptor `rowCount` to be canonical non-negative integer text (`^(0|[1-9][0-9]*)$`), rejecting fractional/`2.0`/leading-zero/signed forms with `invalid restore manifest descriptor` before any `text::integer` cast. The accepted `snapshotSequence` range is made explicit as `[0, 2^63-2]` (must be `< 9223372036854775807`) so the single post-commit increment (`sequence = restored + 1`) cannot overflow bigint. Restore round-trip integrity is proven by a populated fixture that exports a full ledger, rewrites the owner to a foreign id, wipes, restores, and asserts a re-export reproduces every table byte-for-byte and remaps all rows to the caller.
- Rationale: Counts were validated only as JSON `number`, so a fractional value slipped past the type check and blew up on an uncaught `22P02` cast instead of failing closed; and the sequence range admitted int64 maximum, which overflowed on the commit increment. Both are boundary defects in an authoritative recovery path. The empty-table restore test proved none of the insertion, money-canonicalization, FK-ordering, audit, or owner-remapping logic — a populated round-trip with re-export equality closes that gap.
- Consequences: Restore fixtures that hand-author populated payloads must avoid null row fields, because `restore_request`'s `jsonb_strip_nulls` recursively drops nulls from the chunk and breaks the chunk/aggregate digest binding (see GOTCHAS).
- Evidence: `supabase/migrations/202607240006_restore_count_and_sequence_bounds.sql`, `supabase/tests/003_restore_contracts.sql` (fractional-count and int64-max tests fail pre-006; populated round-trip asserts re-export equality and owner remapping), verified via `supabase db reset` + `supabase test db` with migration 006 held out then restored.

## D-014 — Row fingerprints are server-recomputed and rejected on mismatch, guarded by a source-text charset

- Date: 2026-07-25
- Status: Accepted
- Decision: `confirm_import` recomputes every row's fingerprint with `private.row_fingerprint` and raises `fingerprint mismatch` when the caller's claim differs, rather than silently overriding it. `private.normalize_source_text` mirrors `normalizeSourceText` in `lib/canonical.ts` (NFKC, then collapse the JS whitespace set — including U+FEFF, which NFKC does not fold and PostgreSQL `\s` does not match — then trim). `lib/statement.ts` constrains `transactionLabel`, `description`, `reference`, and `branch` to a fixed charset (ASCII, Latin-1/Extended, combining marks, Thai, general punctuation, currency, fullwidth forms, whitespace controls).
- Rationale: The fingerprint is the ledger deduplication key (`unique(owner_id, account_id, fingerprint)` + `on conflict do nothing`), so a claim that does not match its row could silently drop a real transaction or force a spurious dedup. The digest bound the rows including their fingerprints, but nothing bound a fingerprint to the row it claimed to identify. Reject-on-mismatch was chosen over the server-authoritative override originally proposed in PLAN: under both designs the server recomputes, so a future PostgreSQL major version shipping newer Unicode data could derive a different fingerprint for an already-stored transaction. Under override that silently misses the dedup key and inserts a **duplicate ledger row**; under reject it raises loudly at import time. Silent double-counting of real money is the worse failure. The charset guard makes that skew class unreachable rather than merely unlikely, so a mismatch now means tampering or a genuine bug.
- Consequences: Widening the source-text charset re-opens the NFKC skew risk and must be re-validated against PostgreSQL's Unicode data. pgTAP fixtures that need a specific fingerprint (deliberate collisions, wrong claims) must send it via `pg_temp.confirm(..., p_bind_fingerprints => false)`; overlap fixtures must instead carry identical fingerprint inputs so the collision is derived from row content.
- Evidence: `supabase/migrations/202607240007_fingerprint_functions.sql`, `supabase/migrations/202607240008_confirm_import_fingerprint_binding.sql`, `lib/statement.ts`, `supabase/tests/002_security_contracts.sql` (test 23 fails pre-008 with `caught: no exception`, other 29 pass; 84/84 after `supabase db reset` applying 001–008), `tests/domain.test.ts` (charset boundary tests incl. U+1CCF0), SQL/JS parity harness 0 mismatches over 6 fingerprint cases and 50k realistic-charset strings.

## D-015 — Krungthai geometry is read from the pdf.js text layer against invented fixtures

The pdf.js integration itself (transform extraction, page iteration) is not covered by tests. The statement frame is still unextracted, so a PDF cannot yet yield a confirmable payload; the UI reports the row count and stops.

## D-016 — The statement frame is extracted from labelled pairs and reduced to last four at the parser

- Date: 2026-07-25
- Status: Accepted
- Decision: `extractStatement` reads the frame block above the transaction grid on page one — account type, account number, period, opening balance, closing balance, and an explicit THB marker — taking each value from whatever is printed to the right of its label on the same line. The account number is reduced to its last four digits inside the extractor, so no full account number is ever returned. The extracted period end year anchors every two-digit year in the statement, including its own start date. A final cross-check rejects a statement whose last row balance disagrees with the printed closing balance (`CLOSING_BALANCE_MISMATCH`).
- Rationale: Label-relative reading suits a frame, where fields are printed as label/value pairs rather than in fixed columns, and it degrades to a typed `MISSING_FRAME_FIELD` rather than a mis-parse when a label is absent. Reducing to last four at the point of extraction rather than downstream means no later code path, log line, or error message can leak a full account number — the value simply never exists past the parser, which is stronger than redacting it later. Anchoring years on the extracted period end rather than the current year (the prior shortcut) makes parsing deterministic: the same PDF yields the same dates whenever it is read. The closing-balance cross-check catches dropped or misread rows, which row-level validation cannot detect on its own.
- Consequences: Binding an extracted statement to a ledger account is still unimplemented and deliberately so — which `accounts` row a last-four maps to is a user decision the parser must not infer — so a PDF still cannot produce a confirmable payload without that step.
- Evidence: `lib/krungthai-layout.ts`, `tests/krungthai-layout.test.ts` (27 tests; 11 frame-specific, including one asserting the full printed number does not survive extraction), `tests/fixtures/krungthai-layout-v1.ts`, `docs/KRUNGTHAI_CONTRACT.md`. Gate: 59 passed / 1 skipped, ESLint, tsc, production build.

## D-017 — Account binding is a checked user decision, not a parser inference

- Date: 2026-07-25
- Status: Accepted
- Decision: `lib/import-assembly.ts` turns an extracted statement into a confirmable `ImportPayload`. The target account is an input, never inferred from the PDF, but the binding is verified rather than trusted: the chosen account's last four digits and currency must match what was printed, and the rows must reconcile from the printed opening balance, before `importPayloadSchema` is applied as the final authority.
- Rationale: The parser reads an account's last four digits but cannot know which ledger account they belong to — two accounts can share a suffix, and the mapping is the owner's to make. Taking it as input alone would let a mis-click post one account's transactions into another's ledger, which is silent and expensive in an append-only ledger. Checking the printed last four and currency against the chosen account makes that specific mistake impossible without adding an inference. Reconciling client-side duplicates a server check deliberately: the server is still authoritative, but failing here keeps blockers visible next to the rows that caused them.
- Consequences: An account whose last four is unknown to the ledger cannot be bound until the owner records it. The HTTP path is still unexercised — see PLAN task 3 for the two blockers (local auth env is out of scope to inspect, and owner identity requires Google OAuth, an explicit authorization gate).
- Evidence: `lib/import-assembly.ts`, `tests/import-assembly.test.ts` (6 tests, including account/currency mismatch, a non-reconciling row, and a charset violation, plus one that mirrors the confirm route's fingerprint + digest steps).

## D-018 — Advisory lock serialization is proven with two real connections

- Date: 2026-07-25
- Status: Accepted
- Decision: `tests/advisory-lock.test.ts` verifies the owner mutation advisory lock by contending for it from two separate PostgreSQL connections: a tagged holder session takes `pg_advisory_xact_lock(hashtextextended(owner || ':ledger-mutation', 0))` and sleeps, while a second session attempts the same key under `lock_timeout`. Three properties are asserted — the same owner is blocked (55P03), a different owner is not, and the lock frees when the holding backend ends.
- Rationale: pgTAP cannot cover this. Its tests run in one session inside one transaction, and a session that already holds an advisory lock re-acquires it without blocking, so a single-session assertion passes whether or not the lock does anything — it is not a distinguishing test. The different-owner case is the control that makes the same-owner timeout meaningful: without it, a `tryAcquire` that failed for any unrelated reason would look like correct serialization.
- Consequences: The test needs the local container and skips loudly when it is unreachable, so a skipped run is not evidence of serialization. It exercises the lock key directly rather than through the RPCs, because reaching those needs an authenticated owner (PLAN task 3, blocked).
- Evidence: `tests/advisory-lock.test.ts` (3 assertions, ~5s), GOTCHAS entries on blocked-event-loop stdin starvation and `docker exec` kill semantics, both found while building it.

## D-019 — The recovery chain is proven end to end at scale, non-destructively

- Date: 2026-07-25
- Status: Accepted
- Decision: `tests/backup-roundtrip.test.ts` drives the whole schema-v2 chain over 1,200 source transactions: export, contract validation, encrypt, decrypt, staged restore with all eleven chunks in order, commit, and re-export equality. ## D-021 — A statement becomes an import through a chooser, not a code path

- Date: 2026-07-25
- Status: Accepted. Closes the open consequence recorded in D-017 (binding had no user-facing step) and, with D-022, the route-coverage consequence recorded in D-020.
- Decision: `GET /api/v1/accounts` lists the owner's accounts, and `app/ledger-app.tsx` gained a bind stage between parsing and review: the owner loads their accounts, picks one, and only then is `assembleImportPayload` applied and the result posted to `/api/v1/imports/confirm`. The endpoint is an RLS-protected select of an explicit column list (`lib/accounts.ts` is the shared wire contract), not a new RPC. The artifact digest is the SHA-256 of the PDF's own bytes, computed on the main thread before the buffer is transferred to the worker. One idempotency key is minted per bound statement, so a failed confirmation can be retried without becoming a second import.
- Rationale: Everything under the UI already worked — extraction, assembly, confirmation — but only a test wired them together, so the app could not turn a PDF into a ledger entry. A plain select suffices where `list_account_transactions` needed an RPC: accounts carry no nested shape to assemble and no column wider than the last four digits exists to withhold, so the existing `strong_owner_select` policy is the whole enforcement. Digesting the bytes before transfer is the only point where they are still readable on the main thread; a digest cannot be reversed into statement content, and it is what makes re-importing the same PDF a detectable conflict rather than a duplicate ledger.
- Consequences: The `.pldemo` export is now offered only on the synthetic path — wrapping real confirmed rows in a file that calls itself synthetic would misdescribe the artifact. The binding chooser is unexercised in a browser: reaching it needs a real PDF, so Playwright still covers only the synthetic review path, and the flow's parts are covered separately by `tests/import-route.test.ts` and `tests/import-assembly.test.ts`. Binding stays a checked user decision (D-017) — a guard in `tests/privacy.test.ts` fails if the UI ever matches an account to the statement automatically.
- Evidence: `app/api/v1/accounts/route.ts`, `lib/accounts.ts`, `lib/canonical.ts` (`sha256HexBytes`), `app/ledger-app.tsx`, `tests/privacy.test.ts` (10 tests, 3 new). Gate: ESLint, tsc, Vitest 87 passed / 5 skipped, pgTAP 84/84, production build, Playwright 4/4.

## D-023 — pdf.js gets its own worker, and the browser parse path is tested with a generated PDF

- Date: 2026-07-25
- Status: Accepted
- Decision: `workers/krungthai.worker.ts` hands pdf.js an explicit `GlobalWorkerOptions.workerPort` built from a dedicated entry module (`workers/pdf.worker.entry.ts`, whose only job is to import `pdfjs-dist/build/pdf.worker.mjs`). `tests/fixtures/synthetic-pdf.ts` renders the existing invented geometry into a real PDF, and `tests/e2e/parser.spec.ts` drives the running app with it — one test asserts a full parse and the move to the bind stage, one asserts an unrelated PDF fails closed as `UNSUPPORTED_LAYOUT`. The worker now also returns the caught error's class name, and the UI shows it beside the typed code.
- Rationale: `GlobalWorkerOptions` had never been configured, so pdf.js fell back to loading its worker module inline and threw a bare `Error` before reading any page — every PDF was unparseable, and the app's most load-bearing integration was broken. The font is Type0/Identity-H with an identity ToUnicode CMap and no embedded glyph program, because pdf.js recovers text from ToUnicode rather than outlines, so Thai extracts exactly without committing a font binary.
- Consequences: `workerSrc` pointed at the package path is not an alternative — the bundler inlines `pdf.worker.mjs` into the parser worker's own chunk, where it runs in that scope, replaces `self.onmessage`, and posts pdf.js protocol messages to the main thread (GOTCHAS). Returning the error class name is a deliberate, bounded disclosure: pdf.js names are library constants, never document content, and without them every failure except an unsupported layout read identically — which is what made the first real-statement attempt uninformative. Encrypted PDFs remain untested by generated fixtures; the generator writes no encryption dictionary, so the password path is still only exercised interactively.
- Evidence: `workers/krungthai.worker.ts`, `workers/pdf.worker.entry.ts`, `tests/fixtures/synthetic-pdf.ts`, `tests/e2e/parser.spec.ts`. Gate: ESLint, tsc, Vitest 87 passed / 5 skipped, Playwright 8/8 across desktop and mobile (was 4/4). Confirmed distinguishing: both new tests fail with `PDF_PARSE_FAILED / Error` on the pre-fix worker.

## D-024 — The column model follows a real statement, corrected by the smoke test

- Date: 2026-07-25
- Status: Accepted. Corrects the invented geometry of D-015 and D-016, whose column model no real statement could satisfy.
- Decision: The reader's columns are `Date/Time`, `Transaction`, `Description/Cheque No.`, `Withdrawal`, `Deposit`, `Balance`, `Branch`. Date and time share one cell, parsed together as `dd/mm/yy` with an optional `HH:MM(:SS)`. ## D-029 — A printed zero money column is no movement, not a rejection

- Date: 2026-07-25

## D-031 — The statement's calendar era is determined once, from its period end

- Date: 2026-07-25
- Status: Accepted. Replaces `resolveKrungthaiYear`, which assumed Buddhist Era unconditionally.
- Decision: `resolveStatementEra` reads the frame's period-end year in both calendars and keeps whichever lands inside a plausible window for an importable statement (20 years back, 1 year forward). Exactly one can, because the two readings are always 543 years apart and the window is narrower than that; if neither fits it throws and the frame fails closed with `INVALID_FRAME_CONTENT`, and the unreachable both-fit branch throws rather than choosing. The resolved era is threaded to every row through `gregorianYearFrom`, so a statement is never read half in one calendar. The era is returned beside the frame, not inside `StatementFrame`, which is hashed into the import digest.
- Rationale: A real English-language statement prints `26` for 2026. Read as Buddhist 2569 that is 1983, and `2500 + 26 - 543 = 1983` is exactly what the bind screen showed. Every row inherited the same 43-year shift, because rows anchor on the period-end year. **This is the first defect in the sequence that did not fail closed** — the statement parsed cleanly, reached the bind stage, and would have written 1983 dates into an append-only ledger. It was caught only because the bind screen prints the period. Determining the era from the 543-year separation is arithmetic, not a heuristic: a test walks all 100 two-digit years and asserts the ambiguous branch is unreachable (Gregorian admits 06–27, Buddhist 49–70, disjoint).
- Consequences: A statement older than 20 years, or dated more than a year ahead, is now refused outright — deliberate, since neither is importable and the alternative is a silent 43-year error. The window cannot be widened past ~43 years without making the two calendars genuinely ambiguous; the guard makes that failure loud rather than silent. Era detection rests on the period end being present and parseable, which D-026 already requires. The same fix corrected an adjacent defect: the period *start* previously inherited the end's year outright, so a range crossing a new year dated the start a year late — it now resolves its own printed year in the resolved era, which is what revealed the real statement's period to be 13 months (2025-07-01 to 2026-07-31) rather than one.
- Evidence: `lib/dates.ts` (`resolveStatementEra`, `gregorianYearFrom`, `StatementEra`), `lib/krungthai-layout.ts` (`extractFrame`, `toRow`), `tests/domain.test.ts` ("decides the statement era from its period end, refusing an implausible year"), `tests/krungthai-layout.test.ts` ("reads a statement printed in Gregorian years rather than as Buddhist 1983", "resolves a period start that crosses a new year against its own printed year"). ## D-033 — The import is cross-checked against the statement's own printed totals

## D-035 — Private statements are invoked, never read: the masking harness boundary

- Date: 2026-07-25
- Status: Accepted. Records the access grant referenced in `HANDOFF.md` § Standing authorizations and amends the reach of D-001 and `docs/FIXTURE_POLICY.md`; it does not supersede either.
- Decision: The owner granted direct access to `private-statements/` after offering it three times and being declined twice. The grant is bounded to **invoke, don't read**. An agent may run `scripts/mask-statement.mjs` against a file *or a directory* in that directory and may read the masked dumps the harness writes to the gitignored `masked-dumps/`. An agent may not open, list the contents of, copy, or otherwise read a file under `private-statements/` itself, and no tool call may pass a statement's bytes or page text back into a session. **File names are masked** on the same terms as cell text, which is what makes the no-listing rule cost nothing: directory mode means no real name is ever typed or read, and a dump names its source as `xxxx_dddddddddd_dddddd.pdf`. The owner offered listing access on 2026-07-25 and it was declined in favour of this, because statement names routinely carry an account number or the holder's name. The harness reads the document password from stdin only — never from a chat message, a repo file, an environment variable, or a command-line argument — and needs it once per file, to produce that file's dump. The dump carries only what the on-device diagnostics already emit (`maskShape`, `describeLabelGeometry`, `describeValueLabels`, `describeStructure`), which `tests/privacy.test.ts` holds to shapes, coordinates, and digit-free label wordings.

One dump per format collapses that to one owner-driven invocation, after which the layout can be developed offline. The narrower path — a masked dump rather than the document — keeps the two properties the earlier refusals were protecting: no real transaction, counterparty, amount, or account number enters a session transcript, and "the fixtures are invented" stays falsifiable, because nothing an agent can see carries a value to copy.
- Consequences and cost, stated plainly:
  - **Once an agent holds folder access, "no values reach the agent" is discipline, not structure.** Nothing in the tooling prevents a future session from reading a PDF directly; only this entry and the policy amendment do. That is a real reduction in the guarantee and is the price of the grant.
  - **An agent's reads are transmitted and retained in a session transcript.** The owner's earlier belief that agent reads stay on-device is false. The app's on-device guarantee (D-003, and the "No data left this device" UI string) belongs to the *app*, not to an agent. If a future session finds the owner reasoning from the older belief, correct it before acting on this authorization.
  - **The passwords are identity-grade and non-rotatable** — the owner's date of birth and citizen ID. The owner considers them low-sensitivity; they are the opposite. A password in chat or in a shell argument cannot be recalled: chat is retained, and an argument is visible to every process on the machine and lands in shell history. Hence stdin only.
  - **A dump is not a fixture.** It records a real document's structure, so committing one, or transcribing its coordinates and label wordings into a fixture, would make every fixture written afterwards non-invented. `masked-dumps/` is gitignored and `docs/FIXTURE_POLICY.md` now says this outright.
  - **A dump is masked, not empty of text.** Label wordings are printed unmasked, because a wording is exactly what they exist to reveal. No value can reach them — a run carrying a digit is dropped, so is one over 24 characters, and a label qualifies only when the run to its right is a number, which is why an account holder's name cannot appear. But the filter is structural, not semantic: on an unfamiliar layout, short digit-free text printed left of a number need not be boilerplate, and on a receipt it could be a merchant or recipient name. Verified on the synthetic fixtures, where the section correctly returns the frame labels, the summary labels, and the Thai transaction-type vocabulary and nothing else. The dump labels that section as the one to check, and the harness says so when it finishes. Receipts are the case to watch, since their layout is entirely unknown (task 11).
  - The grant does not extend to `.env*`, which remains off limits to agents under `PLAN.md` task 10.
- Evidence: `scripts/mask-statement.mjs`, `docs/FIXTURE_POLICY.md` § Masked structural dumps, `.gitignore` (`masked-dumps/`), `tests/privacy.test.ts` (the harness may not print raw page text, and the four diagnostics remain value-free). The grant itself is recorded in `HANDOFF.md` § Standing authorizations.

## D-036 — A development sign-in, gated by an opt-in flag rather than by `NODE_ENV`

- Date: 2026-07-25
- Status: Accepted
- Decision: `app/api/v1/dev/session/route.ts` signs in as the seeded synthetic owner, enrols and verifies two TOTP factors, and leaves an `aal2` `@supabase/ssr` cookie session — the session every owner-bound route requires. It is reachable only when all three of these hold, and any one missing gives a 404 rather than a 403, because a 403 confirms the route exists: `NEXT_PUBLIC_ALLOW_DEV_OWNER_SESSION` is exactly `"1"`; the configured Supabase URL is loopback; and the request's own `Host` is loopback. The route takes no request body, so it cannot be asked to sign in as anyone else. The matching UI button is not rendered in a build without the flag, because the bundler inlines the missing variable as `undefined` and the comparison fails. **This is not the login** — the real one is Google OAuth (`docs/PRODUCT_CHARTER.md`, `docs/ARCHITECTURE.md`).
- Rationale: three paths had never run in a browser — the binding chooser, the authenticated import path, and the charset rejection path — because the app has no sign-in at all, and every one of them sits behind an owner-bound route (`PLAN.md` task 10). A local password session satisfies the gate exactly as a Google identity would, because `private.has_strong_owner_access` checks the bound owner, `aal2`, and two verified TOTP factors and never inspects the auth provider (D-020); provider verification happens once, at binding.
- Why not `NODE_ENV !== "production"`, which was the first design: the browser suite must run against `next build && next start`, because the strict CSP forbids the `eval()` React needs in development mode, so under `next dev` the app never hydrates and no click does anything (GOTCHAS, "Strict production CSP can block the Next.js development runtime"). A `NODE_ENV` guard is therefore unreachable in exactly the build that has to exercise it. The alternative — relaxing the CSP with `unsafe-eval` for development — is refused by that same GOTCHAS entry and by the standing CSP invariant. The flag is the weaker guard of the two and it is chosen deliberately, because it is the one compatible with never weakening the CSP.
- Consequences, stated plainly: **this is weaker than "impossible in production".** A deployment that set the flag, pointed at a loopback Supabase, and was reached over localhost could serve it; `NODE_ENV` could not be spoofed that way. What is true is that the flag is absent by default, must be present at *build* time for the button to render, and is set nowhere in the product — only in `playwright.owner.config.ts`. One smaller correction, since an early draft of this entry overstated it: a build without the flag does not render the button, but the string `Dev sign-in` is still present in the JavaScript chunk — the bundler kills the branch, not the literal. Verified by searching a normal production build. The route's 404 is the guard that matters; the button's absence is ergonomics. Secondary: the two TOTP secrets are written to the gitignored `.runtime/dev-mfa.json`, because Supabase returns a factor's secret only at enrolment and a later sign-in cannot otherwise produce a code. ## D-037 — Receipts are images, so they are a separate build behind reviewed OCR

- Date: 2026-07-25
- Status: Accepted. Removes the three receipt formats from `PLAN.md` task 11 and opens task 13.
- Decision: The receipts are JPGs, not PDFs. None of the existing reader applies to them — column bands, the frame/grid boundary, the four masked diagnostics and `scripts/mask-statement.mjs` all operate on a pdf.js text layer, and an image has none. They are deferred as their own task. When built, the approach is **template-region OCR with mandatory per-field review**: fields located by pixel region from a per-bank template descriptor, each region OCR'd under a constrained charset, and every money and date value confirmed by the owner against a crop of the exact pixels that produced it before anything is imported.
- Rationale: The owner reports receipts are consistent within a bank and largely consistent across banks, which changes the problem from document understanding to reading known regions of a known template — the same idea as the column descriptors already planned, with pixel boxes instead of text runs. That makes a constrained charset possible per field (an amount is digits, separators and a point), which eliminates the whole `8`↔`B`, `0`↔`O`, `1`↔`l` class of OCR error, and makes structural validation possible: exactly two decimals, a date inside the window `resolveStatementEra` already enforces, a non-empty region. It does **not** make a digit read trustworthy — `3`↔`8` and `5`↔`6` survive all of it, and a misread there is a valid-looking wrong number. That is the D-031 failure shape: parses clean, looks right, silently wrong, in an append-only ledger.
- Consequences: The review step is the actual protection and is non-skippable, so the automation saving over typing four fields is modest for a one-transaction receipt — accepted deliberately, because the owner wants many receipts handled at once. Reviewing a whole receipt would be theatre; showing one field's crop beside its extracted value is a real check, and it is possible only because the templates are fixed. A masked dump for an image is the OCR boxes with the recognized text put through `maskShape`, so the same invoke-don't-read boundary as D-035 holds: shapes and coordinates reach an agent, values do not.
- Open before any of it starts, and none of it assumed: whether tesseract.js runs under this CSP at all (`'wasm-unsafe-eval'` is allowed and `connect-src` is `'self'`, so training data must be self-hosted rather than CDN-loaded — unverified); whether the dependency and Thai training data can be installed offline from the existing pnpm store; and whether the receipts are screenshots (clean, axis-aligned) or photographs (skew, glare, fading), which decides whether preprocessing is needed at all. One masked receipt dump comes before any design claim, per the same discipline `PLAN.md` already applied to layouts.
- Evidence: none yet, by design — this records a scope correction and an intended approach, not an implementation. `PLAN.md` task 13.

## D-038 — What may appear in a masked dump is decided structurally, not by density

- Date: 2026-07-26
- Status: Accepted. Tightens the mechanism D-035 relies on; does not supersede it.
- Context: the first real use of the masking harness put **real counterparty names into a session transcript** — merchant names from an SCB statement, eight of them. No amount, balance, date, or account number escaped; the structural dump was sound throughout. The leak came from `describeLabelGeometry`, the section D-035 had described as safe, while the section its own warning pointed at was clean.
- Decision, in two rules that a reported line must both satisfy:
  1. **No item anywhere on the line may contain a digit** — the whole line is dropped, not just the digit-bearing items. A transaction row always carries a date or an amount; a heading row never does. This is the rule that holds.
  2. The same items must appear at the same vertical position on at least two pages, which is what a running header structurally is. Defence in depth, since a wrapped description could in principle be digit-free. A single-page document therefore reports nothing and is diagnosed from `describeStructure`, which is masked throughout.
  Separately, `maskShape` now masks to `?` everything outside an allowlist of format-bearing punctuation, rather than keeping whatever was neither letter nor digit.
- Rationale: the original rule was "a dense line is a heading" — at least three short digit-free items. A real SCB statement prints every transaction as `<code> | DESC : | <merchant>`, which is exactly that. The first replacement used position alone, reasoning that rows move down a page while a header does not; that was wrong, because rows sit on a fixed pitch, so the same `y` recurs on every page and a frequent merchant lands in the same slot twice — two of the eight survived it. The `maskShape` change came from the same round: a KBANK glossary embeds subset fonts with no usable `ToUnicode`, so Thai and Chinese decoded to arbitrary symbols like `⤎ ⁄ ⏟ ® £ ¤`, which are neither letters nor digits and so passed through verbatim. Unreadable, but a deterministic remapping of real content that anyone holding the font's cmap could undo.
- Consequences: two design lessons worth more than the fix. **One bank's evidence made an unsafe rule look safe** — Krungthai never tripped the density rule, and it survived a privacy review, a decision entry, and a published claim before a second layout broke it. And **a test fixture that is easier to satisfy than the document proves nothing**: the first regression test omitted the date and amounts a real row necessarily carries, which is exactly why it passed against a rule that did not hold. The fixture now carries them.
- Evidence: `lib/masked-diagnostics.ts` (`describeLabelGeometry`, `maskShape`, `FORMAT_CHARACTERS`), `tests/privacy.test.ts` ("never reports a transaction row, however heading-shaped it looks", "masks a character that decoded to a symbol rather than letting it through"). Confirmed against the real statements: re-running the harness on the same 12 SCB documents reports only the two heading lines, English and Thai, and no counterparty. Gate: ESLint, tsc, Vitest 125 passed / 6 skipped against the live container, Playwright 10/10 isolated and 3/3 owner-session, production build.

## D-039 — A slash-joined money heading is two right-aligned columns, and direction is arithmetic

- Date: 2026-07-26
- Status: Accepted. Corrects `docs/SCB_CONTRACT.md` and `docs/KBANK_CONTRACT.md` as first written on 2026-07-26; does not supersede D-035, which produced the dumps both were derived from.
- Context: the first drafts of both layout contracts were wrong about the single most consequential field, in opposite ways. SCB's said *"One signed money column, not two. `Debit/Credit` is a single column; direction is not encoded by which column the figure sits in."* KBANK's listed `Withdrawal / Deposit` as one of five heading anchors and said nothing about a split at all. Building either as written would have read **every deposit as a withdrawal** — a clean parse, a plausible ledger, and an inverted sign on every credit, which is the D-031 failure shape in an append-only ledger.
- What the dumps actually show, on three independent lines of evidence:
  - Across all 12 SCB statements every row carries **exactly one** run in the money region — never none, never two — and those 361 runs right-align into two tight clusters with nothing between them. KBANK's 89 rows do the same, with the two clusters closer together.
  - SCB's summary block right-aligns `TOTAL AMOUNTS (Debit)` on one cluster and `(Credit)` on the other, and prints the two `TOTAL ITEMS` counts on those same edges. The document labels its own columns.
  - The balance chain agrees: a left-cluster run always decreases the printed balance and a right-cluster run always increases it. `kbank-03` shows it at its cleanest — one right-cluster run takes the balance from tens to tens of thousands and the next row's left-cluster run, **the same printed shape**, takes it back to single digits.
- Decision, in three parts:
  1. **Direction is derived from the balance chain**, not from geometry: the delta from the previous printed balance is either `+amount` or `-amount` and cannot be both, since a zero amount is already refused. This is arithmetic on printed values rather than an inferred coordinate.
  2. **Geometry must agree, and disagreement fails closed.** Each derived direction must occupy one tight cluster of right edges and the two clusters must be distinct, with withdrawals left of deposits as both headings name them. Redundant with the chain by construction and kept deliberately: it is the check that catches the reader picking the wrong run as the balance, which is the shape of D-030.
  3. **Right edges, not midpoints.** For a right-aligned column the right edge is the invariant; a midpoint moves with the value's width, which is what a long figure exploits.
- A second correction in the same pass, for the same reason: **a layout is identified by its heading anchor set, never by a bank name.** A masked dump masks every letter, so it cannot reveal what name a statement prints — the claim would be unfalsifiable against the only evidence available. It would also be wrong: both KBANK statements print `Internet/Mobile SCB` as an ordinary channel, so a signature matching `SCB` routes every KBANK statement to the SCB reader. A bank's name appears on other banks' statements because that is what a transfer is. Krungthai keeps its own name signature, which is proven against a real statement, and is tried only after the heading sets fail to match.
- Consequences: the heading anchors do **not** bound the data columns in either new layout, so `lib/krungthai-layout.ts`'s midpoint banding could not be reused and `lib/statement-layout.ts` reads an ordered row grammar instead. That is why the Krungthai reader was left alone rather than generalized — the abstraction that would have fitted one layout does not fit three.
- Evidence: `lib/statement-layout.ts` (`assignDirections`, `verifyMoneyColumns`, `matchLayout`), `tests/statement-layout.test.ts` ("reads its credit as a deposit", "refuses a figure printed in the wrong money sub-column" for both layouts, "keeps a KBANK statement whose rows name another bank on the KBANK reader"). Distinguishing: disabling `verifyMoneyColumns` fails exactly the two misfiled-column tests and nothing else. Gate: ESLint, tsc, Vitest 154 passed / 6 skipped, pgTAP 90/90, production build, Playwright 14/14 isolated and 5/5 owner-session.

## D-042 — A reader must say how much of the parse it managed to verify

- Date: 2026-07-27
- Status: Accepted. Makes visible the compromise D-033 accepted; does not change it.
- Context: the first real SCB and KBANK reads both succeeded, and in doing so showed that the owner cannot tell a verified import from an unverified one at the moment of confirming it. The status line reported a row count, an account suffix and a period. It did not say which of the three layouts had read the statement, and — the part that matters — it did not say whether the rows had been checked against the statement's own printed counts and totals.
- Why that is not cosmetic: `extractTotals` returns nulls when no summary label matches, `verifyTotals` skips every null, and the statement is then accepted with **no global check at all**. D-033 chose that deliberately, because not every layout prints such a block and refusing one that does not would reject a readable statement. The consequence is that a 55-row import whose count the bank itself confirmed, and a 55-row import where nothing would have caught a dropped row, produced identical screens.
- Decision: `StatementFrame` carries `crossChecked`, true only when a summary block was read in full — **all four** per-direction counts and totals — and agreed with the rows. A partially readable block is false: it confirms part of the parse, and calling that cross-checked overstates it by exactly the amount that matters. Krungthai's `Total Page` does not count towards it, because a page count confirms nothing about rows. The bind stage names the layout that read the statement and states plainly whether it was cross-checked, with the unverified case rendered as an alert — that screen is the last point at which the owner can decline.
- Why on the frame rather than beside it: `balancesPrinted` is already exactly this kind of flag — how much verification the document permitted — and lives there. Adding a second one changes no committed contract: `assembleImportPayload` copies named fields out of the frame rather than spreading it, and `confirmationDigest` hashes only the account, contract version, currency, period, balances and rows. (Older wording in `PLAN.md` and `HANDOFF.md` said "`StatementFrame` is hashed into the import digest". It is not; the payload built from it is. Corrected in the same pass.)
- What this deliberately does **not** do: persist it. Whether an import was cross-checked is still recorded nowhere in the ledger, so a committed batch cannot be distinguished after the fact. That is `PLAN.md` task 12, it needs a migration and a payload-contract change, and it needs an owner decision first on what a missing cross-check should mean for an already-committed import.
- Evidence: `lib/statement-frame.ts`, `lib/statement-layout.ts`, `lib/krungthai-layout.ts`, `app/ledger-app.tsx`. ## D-043 — An import the bank's arithmetic did not confirm is refused, not labelled

- Date: 2026-07-27
- Status: Accepted by the owner. Closes `PLAN.md` task 12 and settles the question D-033 left open; supersedes the part of D-042 that rendered the unverified case as a warning the owner could proceed past.
- Decision: `assembleImportPayload` refuses a statement whose `crossChecked` is false, with `NOT_CROSS_CHECKED`, before it checks anything about the binding. Nothing is persisted and no migration is needed, because nothing unverified can reach the ledger to be labelled.
- What decided it, and it is not what it first looked like. The cross-check appeared to be the main defence against a dropped row; it is not. `reconcileRows` and `confirm_import` both require `previous + movement = printed` on every row, so a dropped **middle** row surfaces as a gap at the next row and is already refused. What the balance chain cannot see is narrow, and differs per layout:
  - a dropped **first** row is invisible on Krungthai, whose opening is derived from row one (D-026), and caught on SCB and KBANK, which print a brought-forward balance;
  - a dropped **last** row or trailing page is invisible on Krungthai and SCB, neither of which prints a closing balance, and caught on KBANK, which prints `Ending Balance`.
  So the cross-check earns its keep precisely where the printed balances run out — and most of all on Krungthai, the layout with 233 real rows already read through it.
- Why refusing costs almost nothing: **all three known layouts print a summary block** — Krungthai's confirmed on the real statement (D-033), SCB's in all twelve dumps, KBANK's in both. A gate therefore never fires on a document that has been seen. Its whole cost is future variants, and that cost is recoverable: the reader learns the wording and the statement imports. The alternative's cost is not — an unverified row in an append-only ledger can only be removed by restoring from a backup taken before the import.
- Rejected alternatives, and why:
  - *Persist a label and import anyway.* The ledger could then answer "which imports were verified?", but the default path would write unverifiable rows permanently, against D-033's own reasoning that an append-only ledger cannot take back a dropped row.
  - *Refuse with a recorded override.* Better, and the natural upgrade if a real statement is ever refused — but designing an override today means designing it for a document nobody has seen. Wait for the example.
  - Both alternatives share a flaw worth recording: the server cannot recompute `crossChecked`, because it never sees the PDF, so a persisted flag would be a **caller's attestation** — weaker than everything around it, since D-012 rebinds the payload digest server-side and D-014 recomputes every fingerprint. Making it a fact rather than a claim would mean sending the statement's printed counts and totals in the payload and having `confirm_import` re-verify them against the rows it is storing. That is the shape any future option C should take.
- Where the refusal lives, and why not in the reader: the reader still reads such a statement. What a document contains is a fact, and the diagnostic that fixes a wording mismatch depends on the parse succeeding. Putting the gate at the import boundary also keeps a dozen fixtures that never print totals readable, instead of coupling every layout test to this policy.
- Consequence, and the one that makes the refusal actionable: the worker now sends `describeValueLabels` with a **successful** parse when `crossChecked` is false, so the bind screen can show the candidate summary wordings the statement actually prints. Without it the owner would meet a refusal with nothing to act on, since that diagnostic previously existed only on the failure path. It crosses on the same terms as before — reduced to a local before the post, never `pages`, and `tests/privacy.test.ts` holds it there.
- Evidence: `lib/import-assembly.ts` (`NOT_CROSS_CHECKED`), `workers/krungthai.worker.ts`, `app/ledger-app.tsx`, `tests/import-assembly.test.ts` ("refuses a statement whose printed totals never confirmed its rows", "names the missing cross-check before anything about the binding"). Distinguishing: disabling the guard fails exactly those two tests and nothing else. Gate: ESLint, tsc, Vitest 158 passed / 6 skipped against the live container, production build, Playwright 14/14 isolated and 5/5 owner-session. pgTAP not re-run — no SQL, migration, or database code changed; last run 2026-07-26, 90/90 across migrations 001-009.

## D-050 — Slips are provisional entries the statement confirms, and their images are not stored

- Date: 2026-07-28
- Status: Accepted as direction. Nothing built; this records a design the next session should follow rather than re-derive.
- Context: the owner wants daily capture from bank-app transfer slips (K PLUS, K NEXT, SCB Easy) with statements imported weekly or monthly, and cash purchases entered by hand. Three real samples were assessed.
- What the samples established: they are **app screenshots, not thermal paper**, so the hard OCR case does not apply — crisp, high-contrast, fixed layouts. All three QR codes decoded first try with no upscaling. The payloads are EMVCo TLV (the Thai slip-verification format): bank code, a unique transaction reference and a CRC, and **no amount**. Three banks meant three entirely different layouts, and the SCB sample was a bill payment, so transfer variants are unseen — assume more layouts exist, as `KBANK-01.pdf` taught the same day.
- Decision: a slip is a **provisional entry**, not an authoritative row. The statement remains the authority and reconciles against slips already captured. This preserves the invariant the whole ledger rests on — every authoritative import is cross-checked against the bank's own printed totals, and a slip has no arithmetic to check against, so promoting slips to authoritative would invert the trust model.
- Decision: **the QR supplies identity, OCR supplies values, and the owner confirms.** The QR is exact and free of OCR risk, so it carries the dedup key and the statement-matching key — the part that is catastrophic to get wrong. Amount, date and merchant are proposed and never auto-confirmed, reviewed against the image with region-targeted OCR and a digit whitelist rather than whole-image recognition.
- Decision: **slip images are not stored.** Storing them either bloats the backup from 14 KB to hundreds of megabytes, or sits outside it in Supabase Storage and costs the property that one file restores the whole ledger. The images already exist in the owner's Google Photos, better backed up than the app would manage. What is stored is the QR payload, the extracted values, and optionally an image hash — "store what you cannot reconstruct". A thumbnail is the fallback if browsing ever demands one; it is easy to add and painful to remove at 3,000 rows.
- Rejected: a paid slip-verification API (Thunder 150/month free then ~199 ฿/month; SlipOK from 210 ฿; EasySlip from 350 ฿). Its only benefit is same-day authority, which the statement supplies free a week later, and it would send every transaction reference to a third party — awkward for an app premised on the data staying the owner's.
- Rejected: syncing the owner's three Google Photos albums. Google removed the `photoslibrary.readonly` scope on 2025-03-31; apps now reach only media they created, and anything else returns `403 PERMISSION_DENIED`. The Picker API replaces it and requires explicit per-session selection. **Share-to-app is preferred anyway** — an installable web app with a share target captures each slip at the moment of payment rather than from a roll at midnight, needs no Google scope, and retires the albums as a pipeline.
- Build order, and why: **manual capture first, OCR second.** The form is identical either way; OCR only changes where the initial values come from. Building the cheap half first means a bank whose slips read badly simply stays manual, and nothing is wasted.
- Watch for: Buddhist-era dates in two shapes across the samples (`24 ก.ค. 69` and `23 ก.ค. 2569`) with Thai month abbreviations. The 543-year shift already parsed cleanly into 1983 dates once (D-031) and must fail closed here too.
