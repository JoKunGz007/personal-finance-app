# Private Ledger specification index

Last reviewed: 2026-08-27

This file is the stable entry point for project requirements. It summarizes only the cross-cutting contract and links to the detailed specifications that own the exact behavior.

## Product objective

Private Ledger is a local-first, single-owner application that converts a supported bank statement — Krungthai, SCB, or KBANK — into a reconciled, reviewable ledger without exposing the PDF, its password, or private financial data. Bank slips are images, captured through the app as provisional entries the statement later confirms (D-050, `PLAN.md` tasks 20–22); the OCR-first framing of D-037 is superseded, and cash receipts are entered by hand. **Slip capture is built as of 2026-07-30** (D-056, migration 011): a slip's identity comes from its QR — bank and transaction reference, checked against the payload's own CRC — while the amount, date and counterparty are the owner's, typed and confirmed. A slip is never authoritative and never carries an account; the statement stays the authority. **No slip image is stored**, in the database or anywhere else.

**Slip capture reads the amount through Google Cloud Vision and offers it, as of 2026-08-18** (D-129, task 36 done; task 21 shipped the finder this replaced). The image goes to `POST /api/v1/ocr/read`, which holds the API key so the browser never does — the strict CSP is unchanged, `connect-src` still naming `'self'` and the Supabase origin alone. **There is no local engine and no fallback to one**: `lib/slip-ocr-engine.ts`, its self-hosted assets and the `tesseract.js` dependency are all deleted. A read that fails leaves the box empty and the owner types the figure. **A figure may reach the amount box only through `proposeAmount`**, which requires it to parse as printed money beside the amount's own label — so `parseThb`, the two-fractional-place rule and blank-on-failure all sit downstream of whatever engine produced the words, and no engine can put a wrong-but-plausible figure in a box. This **reverses D-087's rule for slips**, on a measurement of the engine that replaced the one D-087 measured: located on 23 of 23 real samples against tesseract's 16, parsing as money on 23 of 23 (D-128). **What is still not established is whether an offered figure is the *right* figure** — the statement is the independent check, exactly as for cards: a wrong amount fails to pair and surfaces as unmatched. **Slip identity stays the QR's** and is never machine-read.

**Slips are reconciled against statement rows as of 2026-08-01** (D-063, task 22 half done, read-time only). No layout prints the transaction reference the QR carries, so a match is inferred from bank, an amount equal to the minor unit, and the nearest date **within one day** (narrowed from three on 2026-08-05, D-064: the owner's banks post same-day, so the window is tolerance for the slip's clock and the bank's straddling midnight, not for a late posting) — and is made only when that pair is mutually unique, so two identical payments refuse rather than guess. A matched pair is shown as one row, the statement's, which is what lets the ledger's totals count each payment exactly once. **The owner's override and undo are stored as of 2026-08-05** (D-067, migration 012): a decision names the statement row or says there is none, it is audited and revisioned, its history is append-only, and it is applied **before** the automatic rule so an explicit decision can never lose to a proposal. A statement row can be claimed by at most one slip, enforced in the database rather than only by the reader. **The decision is reachable from the app as of 2026-08-07** (D-068): the ledger row carries the control, `PUT /api/v1/slips/[id]/match` is the only caller of the RPC, and the stored decisions travel on the same response as the slips they are about. What an override may assert is deliberately narrow — the same bank and the same amount to the minor unit — so it resolves ambiguity and rejects a wrong pairing without being able to declare two different sums one payment.

**Cash and corrections complete task 22 as of 2026-08-10** (D-084, migrations 013 and 014, on the synthetic project only). A cash payment is a ledger fact with no statement behind it: its own table rather than a statement row, no account, no printed balance, and **never matched to anything** — there is no row it could collapse onto, now or later — so it is counted apart from provisional slips rather than folded in with them. What the owner typed on a slip or a cash entry is **correctable; what the QR carried is not** — a slip's bank and reference are absent from the correction overlay entirely, because a correctable identity would let one slip be re-typed into another's. Neither record is ever edited: both tables are append-only, a correction is a separate overlay with an append-only history, and both figures survive a backup. The **amount in force is resolved once, at the edge of the read path**, so the match rule, the totals and the row cannot disagree about which figure is real — migration 014 exists because the database's own guard once compared a slip's original amount against a statement row, refusing correct pairings and accepting wrong ones.

**A bank's LINE push notification can be captured and reconciled as of 2026-08-13** (D-098 through D-102, migration 016, `PLAN.md` task 27, which is complete). The table, its identity rule and its write path landed first (D-098), then the printed grammar (D-099), the reader (D-100), the capture form with its route (D-101), and finally the ledger view and the reconciliation (D-102). **The printed balance is what a card reconciles on, and it is the field a slip has never had**: it breaks the tie between two rows of the same amount that the slip rule refuses outright, and a card that fits on account, amount and date while contradicting every such row's balance **refuses to pair** rather than pairing on what agreed. It is a tie-breaker and a fail-closed cross-check, **not identity** — measured equal to the statement row's on 6 of 6 real cards, but none captured while a hold was outstanding, and *available* and *remaining* balances diverge exactly then. **A card's typed figures are correctable and its pairing is the owner's to overrule, as of 2026-08-14** (D-104, migration 017, task 29 complete). The balance is correctable like any other figure the owner read off a screenshot; **the binding is not** — the account, the channel and the printed digits have no column in the overlay, because the check that bound them cannot be re-made after capture. A balance disagreement is **refused by default and storable only with an explicit acknowledgement**, and what is stored is that consent rather than a comparison that would go stale after a correction. A card captured wrongly is **retired** (`not-a-payment`), which takes it out of the ledger and the totals while leaving the append-only row intact, and is reversible. The backup is at **v7**, carrying four further tables, with v2 … v6 all still restorable. Three further properties are worth stating here because they are contracts rather than implementation. **A card's four digit-bearing fields — amount, balance, timestamp, account digits — are pre-filled on trial as of 2026-08-16** (D-114, D-115, `PLAN.md` task 34 parts 1 and 2). This **supersedes the rule that all four are typed**, which held from D-087 until that date and is on trial rather than reversed: the fill runs `lib/notification-card-prefill.ts`, which repairs only characters carrying no value, **discards any repair that moved a digit**, runs the same strict `parseThb` the form runs, and leaves a field blank rather than guessing — so no figure can be offered whose digits the engine did not read. A refused field is typed exactly as before. **The direction control is filled from the printed sign as of 2026-08-17, and never from the direction word** (D-123), which supersedes the rule that it was never filled at all. `readDirection` refuses a card whose two printed signals disagree; it takes the **word** from the image and the **sign** from this control, so feeding the word back through the control would make the check agree with itself on every card while still looking like a check. The sign is a different printed feature and a misread of one is not a misread of the other, so the refusal keeps its force. **Where a card prints no sign the control stays blank and the owner sets it** — measured over 28 real cards, 26 print both signals and all 26 agree, the exceptions being KBank Live incoming, which names its direction in the title. The direction is **not** recorded in the pre-fill audit lists: migration 019's closed set is the four digit-bearing fields, and widening it would be a migration. What decides whether this stays is the **statement**, not the edit rate: a wrongly pre-filled figure fails to pair and surfaces as `AWAITING STATEMENT`. **A card screenshot is read by Google Cloud Vision as of 2026-08-17, and it is the one image in this app that leaves the device** (D-120, `PLAN.md` task 35 complete). It is sent to `POST /api/v1/notification-cards/read`, which relays it and returns words and boxes; the key lives in the deployment's environment and never in the browser, so **the strict CSP is unchanged** — `connect-src` still names `'self'` and the Supabase origin alone. Nothing is stored, by that route or anywhere else, and the card form says on screen that the screenshot is sent. **There is no local fallback and that is the decision** (D-120): a failed read blanks every box and the owner types the card, which is what happened before pre-fill existed, whereas two engines behind one grammar would mean measuring every grammar change twice. Through the shipped path at native size over 12 real screenshots: **25 of 25 cards and 99 of 100 digit-bearing fields**, amount, balance and printed account digits 25/25 each, against the local engine's 70 of 100. **The guarantees above are untouched by the engine swap and that is why it was safe**: `parseThb`, the digit guard and blank-on-failure all sit downstream of whichever engine produced the words. The earlier local rates, kept because they are what the guarantee was measured against: on 19 real cards, amount 89%, balance 79%, date and time 63%, own account 58%. **On a slip nothing changed at all** — the amount is located on the device by the self-hosted engine and typed (D-087, D-088), and whether a slip should use Vision too is an open question deliberately answered *no* for now (`PLAN.md` task 36). **The channel comes from the owner, not the card**: SCB Connect and KBank Live print an identical incoming title, so nothing in the card body distinguishes them, and the account-digit mask differs between the two. The route is the only layer that checks the printed digits resolve to the chosen account — the database stores that pairing rather than checking it, and the table is append-only. Not every payment produces the QR-bearing e-slip task 20 reads; when one does not, the bank pushes a card and the owner screenshots it, several times a week. A card is neither a slip (no reference, no QR, and a fingerprint is idempotent rather than tamper-evident) nor a cash entry (cash is never matched to a statement row and a card will be). Identity is computed in the database over the account, channel, kind, amount, timestamp and **printed balance** — the balance being what tells two payments of the same amount at the same minute apart. The card is bound to one of the owner's accounts at capture, and **the year and account-digit rules are per-layout, never global** (`lib/notification-card.ts`), because one layout's convention applied to all three is D-031 exactly. The backup moves to **v6** in the same migration, since a table the export does not carry breaks gate 6 the afternoon it exists.

**Committed data is no longer invented only.** On 2026-07-28 the owner imported one real KBANK statement — 55 rows across 2 pages, cross-checked against the bank's printed totals — into the local ledger, and on 2026-07-29 thirteen more followed (D-054). The fifteenth was refused that day for a balance chain its printed totals could not explain, and imported once the cause was found to be printed order rather than a reader defect (D-055) — taking the ledger to **1,465 rows across 15 batches and three accounts**, which is every statement held. The import happened after the recovery gate passed (D-044) and account creation made binding possible (D-045, D-047). Fixtures, seeds and tests remain invented and always will; what changed is the database, and every constraint below now protects real records rather than synthetic ones. Hosted Supabase, OAuth setup, Vercel, deployment, commits, and pushes still require separate explicit authorization. Local real-statement smoke tests were authorized on 2026-07-25 under stated conditions and were run ten times by the owner, reading a statement end to end; every finding came from on-device masked diagnostics, so no real value entered the repository. Direct access to `private-statements/` was granted the same day under an **invoke, don't read** boundary, and `docs/FIXTURE_POLICY.md` is amended accordingly (D-035) — a masking harness may be run against a statement, and the statement itself may not be read. That directory remains closed; since 2026-07-28 real statements may be read as the password-free copies in `shared-statements/` (D-049), which does not change what may be *written*: fixtures stay invented and no real value is committed, quoted or screenshotted. See `PLAN.md` § Later authorization gates and `HANDOFF.md` § Standing authorizations before acting on any of it.

## Authoritative invariants

- Money is signed 64-bit integer minor units with explicit `THB`. JSON boundaries use canonical decimal strings; binary floating point is never authoritative.
- **Division never produces money** (D-160, 2026-08-27, the first operation in this app that divides one). Totals and subtotals do not divide at all. A **share** travels as its numerator and denominator and becomes a percentage in the presentation layer only — a percentage is a label, nothing is derived from one and none is stored, so shares printed to a fixed precision need not sum to exactly 100. An **average of money is money**, so it is integer division that keeps its remainder, `quotient * divisor + remainder = total` holding exactly for negative totals as well as positive ones. `avg()` and `sum() over ()` both return `numeric` in PostgreSQL, so a money path casts back explicitly and the return types are asserted in pgTAP rather than remembered.
- Source facts, components, provenance, artifacts, batches, overlay history, and audit events are append-only.
- Import, restore, category mutation, retries, and other replayable operations are idempotent or conflict explicitly.
- Dates use the documented statement meaning. Derived instants and reporting boundaries use `Asia/Bangkok`.
- The PDF and password remain inside the dedicated browser worker. Unknown or unvalidated layouts fail closed.
- PostgreSQL is a second enforcement boundary for ownership, reconciliation, immutability, audit, and recovery.
- **`anon` holds no privilege on anything in `public`, and `authenticated` holds `select` and nothing else** — every write goes through a `security definer` RPC. True of future tables as well as current ones since migration 018 revoked the platform default privileges that had been granting `truncate`, `references`, `trigger` and `maintain` to both roles on each new table (D-106, D-107). `truncate` bypasses row-level security, so this is not covered by the policies. **Assert it against the catalog, never against the migration text**: the grant a table actually holds is a database fact, and the defaults that produced it are set outside this repository.
- Strong access requires the bound owner, `aal2`, and **one** verified TOTP factor — narrowed from two on 2026-08-11 (D-093, migration 015, superseding D-004), because reaching `aal2` only ever needed one and the second factor gated nothing while being one more thing to lose. This line said "two" until 2026-08-12 and was wrong for a day: `lib/owner-access.ts` exports `REQUIRED_FACTORS = 1` and `private.has_strong_owner_access` counts `>= 1`. An unverified or non-TOTP factor still counts for nothing.
- Backup freshness means confirmed custody of an encrypted restorable artifact, not merely successful snapshot generation.

## Current local acceptance gate

Before any real-data or hosted stage:

1. A clean local Supabase reset must apply every migration and synthetic seed.
2. Lint, strict TypeScript, unit/property tests, pgTAP, production build, Playwright, privacy checks, and accessibility checks must pass on the current source.
3. Synthetic PDF geometry fixtures must validate the exact supported parser contract before parser support is enabled.
4. Backup export, client encryption, acknowledgement, staged restore, and equality must be exercised end to end with canonical int64 boundaries and more than 1,000 rows.
5. No PDF bytes, passwords, tokens, real values, analytics, service worker caches, or third-party font requests may cross their documented boundary.
6. An encrypted backup must restore into an **empty, separately bound project** — one that never held the ledger and never knew its owner — with every owner and actor identity rebound, including identities embedded in jsonb. A backup covers **every** table holding owner records: one file restores the whole ledger, or the property is lost. Adding a table therefore changes the backup schema version, and **a version the owner still holds a backup in must stay restorable** — the current contract reads **v2, v3, v4, v5, v6 and v7** and writes **v7** (D-056, D-067, D-098, D-104, migration 017). This line read "v6 / writes v6" until 2026-08-15 and was stale from the afternoon migration 017 landed; it was caught by the security review of that migration (D-105), not by a gate, which is the same failure mode as the TOTP factor count on 2026-08-12 — `check:docs` reads structure rather than meaning, so a version number here can contradict the database indefinitely. Read it against `lib/backup-contract.ts` (`BACKUP_SCHEMA_VERSION`, `SUPPORTED_BACKUP_SCHEMA_VERSIONS`) rather than trusting the sentence. New owner data goes in a **new table and never a new column**, which is what keeps that promise cheap enough to keep forever (D-097). **Every project reads v2 … v7 and writes v7 as of 2026-08-15**, the hosted one included — it took 016, 017 and 018 that day and is verified against the remote at 001 … 018 (D-108). Migration 018 moves no version: it changes grants only, adds no table and no column, and a version bump with no table behind it would strand files for nothing (D-107). **The newest file the owner holds is still a v5 one**, taken before that push, so the pair that matters operationally is **v5 into v7** — proven by `restores a v5 file into the current ledger`. `private-ledger-live` stays frozen on 012 and its files are **v4**. Each version keeps its own table list rather than the newest being applied leniently to all, so widening what is accepted is not the same as relaxing it: a v3 manifest does not pass as v4, and a v2 payload carrying a `slips` key is still refused. **The v4-into-v5 pair is exercised as of 2026-08-10** (D-089) — a v4 file stages, chunks and commits into a 014 ledger, the tables it predates stay empty rather than being invented, rebinding is unweakened by the version gap, and the destination re-exports as the current version. That is the pair hosting used, since live writes v4 and the hosted project started on 014. Before that, v4 was covered by the client's schemas and by construction, never by a restore: only v2 (pgTAP) and a real v3-into-v4 (D-078, operational) had ever run. **The v5-into-v6 pair is exercised as of 2026-08-12** (D-098), the same way and for the same reason one step later: the owner's newest file is the v5 export from the hosted project, so that is the pair the next recovery uses, and it was proven before anything depended on it. **The v6-into-v7 pair is exercised as of 2026-08-14** (D-104), one step further on. Three restore tests now name the **file's** version and assert the destination against `BACKUP_SCHEMA_VERSION` rather than naming a destination that moves — `restores a v4 / v5 / v6 file into the current ledger` in `tests/recovery-portability.test.ts`, corrected in `955253c` after three titles went stale the moment 017 landed. So the pair that matters operationally is proven directly: the owner's newest file is a **v5** one, the ledger it would return into is **v7**, and `restores a v5 file into the current ledger` is that assertion. Those three tests **skip** when the recovery destination project is down, and a skipped run proves nothing — read the named line, never the totals.

## Explicit non-goals for the current stage

- No production deployment or hosted resource creation without separate explicit authorization at the time. **This rule is unchanged by having been used.** Hosting and Google OAuth were accepted as direction and sequenced as one move (D-051, `PLAN.md` task 19), then each hosted resource was asked for and granted separately: the Google client and the Supabase project on 2026-08-11 (D-092, D-094), the Vercel project and its deployment on 2026-08-12 (D-096). All of those grants are spent and none is standing — a further project, a custom domain, a second region or any new external service needs its own approval at the time.
- No real statement parsing or smoke test without the owner present. The 2026-07-25 grant has been exercised twelve times and is discharged for all three layouts; it is not a standing licence for unattended runs.
- No multi-user sharing, currency conversion, investment tracking, budgeting, or bank credential storage.
- No statement password in environment variables, logs, database rows, or backup metadata.
- No claim that a synthetic `.pldemo` preview is a restorable backup.
