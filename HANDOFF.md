**The trap is `.env.local`, not the test database.** It points at the live project, and `NEXT_PUBLIC_*` are inlined at build time — so a browser config that runs `pnpm build` without pinning its target builds against real financial records. Since 2026-07-30 the **CSP is inlined from the same variable** (D-058), so a mis-pinned build now also serves a `connect-src` naming the wrong project — which is a louder symptom of the same mistake, not a new one. All three Playwright configs now pin, but `playwright.config.ts` is one of the uncommitted files below, so a fresh clone does not. GOTCHAS carries the variable list and the Windows `$env:VAR = ""` deletion trap that makes a pin look broken.

`pnpm supabase:reset` cannot be guarded and destroys whatever project the working directory names — the repo root names the test project, `live/` names the real one. **Back up through Recovery / 04 before anything destructive, and never set `ALLOW_DESTRUCTIVE_TESTS=1` merely to get a green run.**

## Before you touch anything

- Run `git status --short`. Two kinds of uncommitted file are in the tree and they are not the same thing. **Three config files** — `eslint.config.mjs`, `playwright.config.ts`, `pnpm-workspace.yaml` — are **deliberately local-only**; preserve them, do not commit them. Everything else uncommitted is ordinary work awaiting authorization to commit.
- **`public/zxing_reader.wasm` is generated, not committed.** `prebuild` copies it from `node_modules`, so any `pnpm build` produces it and a fresh clone has it after the first build — but a checkout that has only been installed, never built, has a slip capture that silently decodes nothing (D-057, GOTCHAS).
- **The live project does not have migration 011.** `private-ledger-live` is migrated separately from the `live/` directory, and applying a migration to real financial records has not been authorized. Until it is, an app pointed at `.env.local` has no `public.slips` table and slip capture will fail there — the test project and the recovery destination both have it.
- Check `git status -sb` and `git log --oneline -3` for where `main` stands against `origin/main`. Nothing in this file records that, on purpose.
- `shared-statements/` holds 16 password-free files — 12 SCB, 1 Krungthai and 2 KBANK statements, plus `KBANK-01.pdf`, which is a bank-code reference sheet rather than a statement and correctly refuses with `UNSUPPORTED_LAYOUT`. `masked-dumps/` holds the matching `shared-01…16.md`; sorted order maps to 01–03 KBANK, 04 Krungthai, 05–16 SCB. Both are gitignored working material, never fixtures, and neither contains a receipt — tasks 20–21 need their own samples. **They have now served their purpose**: all fifteen statements are imported, so these password-free copies of real statements are working material with no remaining job. Deleting them is the owner's call and has not been made.
- The recovery destination is a **second Supabase project** and may be left stopped. `node scripts/recovery-destination.mjs up` starts and migrates it, `down` discards it. `tests/recovery-portability.test.ts` skips without it, the Vitest totals read the same either way, and a skipped run proves nothing about recovery. **It does not receive a new migration automatically** — run `up` again after adding one, or the portability test fails on a missing relation rather than on anything real.
- **Docker Desktop shut down mid-session on 2026-07-30 and was restarted.** All three projects came back healthy together and the live ledger was re-verified afterwards at 1,465 rows / 15 batches. A stopped Docker makes the DB-backed suites *skip* rather than fail — 15 green-looking skips is what that looks like, so read the counts, not the colour.
- **Restarting the database container is not enough.** After `supabase db reset` or a `docker restart` of a `supabase_db_…` container, restart that project's `auth`, `rest`, `realtime`, `storage`, `pg_meta` and `kong` containers too. They stay `(healthy)` while holding dead connections, and the symptom is a CLI that cannot connect, a browser suite failing at sign-in with `fetch failed`, or a socket error against the recovery project's port — none of which look like what they are. The recovery project has its own set. GOTCHAS carries the full entry, including why an in-container `psql` check misleads here.
- Never inspect `private-statements/`, `.env*`, or backup files. Preserve the exact-money, currency, idempotency, append-only, audit and least-privilege invariants, and do not weaken the CSP.

Confirmed by grepping `.next/server` for the API URL: two references to the live project's port, none to the test project's.
